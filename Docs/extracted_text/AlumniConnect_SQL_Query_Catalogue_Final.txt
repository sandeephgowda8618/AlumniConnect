Document guide and implementation status
This catalogue converts the AlumniConnect project requirements into a practical set of MySQL query patterns 
and database objects. It is intended to guide implementation, testing, SQL demonstrations and the final DBMS 
project viva. It is not a replacement for the final relational schema: the ER document explicitly treats its entities 
and attributes as conceptual, and reserves physical names, data types and indexes for the relational-design stage.
Important schema boundary  The SQL examples use a consistent snake_case MySQL schema contract defined in 
Section 3. Some column names are implementation choices because the supplied conceptual ER and PRD do not publish a 
complete final CREATE TABLE script. Align those names with your final Relational Design Specification before execution.

1. System and database responsibilities
AlumniConnect is specified as a modular monolith with polyglot persistence. One FastAPI application contains 
the identity, profile, matching, request, allocation, booking, session, feedback and notification modules. MySQL 
8.x with InnoDB is the authoritative relational store. Redis is a cache and temporary-state layer. Neo4j is a 
relationship-oriented projection used to discover and explain mentor candidates.

1.1 SQL belongs at the centre of business correctness
The SQL catalogue is not just a collection of SELECT statements. The project requires query-based screens and 
reports, but the most important SQL routines protect cross-table invariants: accepting one pending request 
creates at most one allocation; booking claims one availability slot; two overlapping appointments cannot be 
confirmed for the same student or mentor; reviews refer to completed sessions; and notifications are only 
emitted for committed business changes.
Transaction rule  The business row change and the corresponding notification / projection intent must be inserted into 
notification_outbox in the same MySQL transaction. The worker performs external side effects after commit.
2. Evolution of the database model
The earlier mini-project defines 12 core tables. The later AlumniConnect blueprint expands the model to separate 
identity, role-specific profiles, domain interests/expertise, recommendation history, mentor availability, 
bookings, sessions, two kinds of feedback, notification outbox and audit history. Keep the earlier model as a 
useful migration baseline, but do not treat every old table as the final model.

3.6 MySQL and naming conventions

Target MySQL 8.x with InnoDB. Use foreign keys, NOT NULL, UNIQUE and CHECK constraints wherever they 
express row-level invariants.

Use uppercase status values consistently in stored values and SQL predicates. Do not mix Pending, PENDING 
and pending in application code.

Store timestamps consistently (prefer UTC at the persistence boundary); format to the user time zone in the 
application.

Use DECIMAL for scores and ratings; never store numeric ratings as VARCHAR.

All code examples are read/write templates. Run DDL and stored routines against a test database first.

The SQL uses MySQL user variables such as @student_id for Workbench demonstration. In FastAPI, bind 
values through prepared statements rather than concatenating user input.

The procedure samples use BIGINT auto-increment identifiers with LAST_INSERT_ID(). If the physical schema 
uses UUIDs or application-generated keys, pass the created IDs into the routine and remove 
LAST_INSERT_ID() calls.

The examples assume primary and foreign keys exist. Add/rename columns only during the final physical-
schema stage.
Security note  Exclude credentials from public views; parameterize user input.

Q02  Public mentor directory
Purpose: Show discoverable active mentors with company and department context.
DBMS concepts: [B/C] Multi-table JOIN; filtering; safe projection of public fields.
SELECT
    mp.mentor_id,
    mp.full_name,
    mp.job_title,
    mp.current_city,
    mp.years_experience,
    c.company_name,
    c.industry,
    d.department_name
FROM mentor_profile AS mp
JOIN user_account AS ua
  ON ua.user_id = mp.user_id
LEFT JOIN company AS c
  ON c.company_id = mp.company_id
LEFT JOIN department AS d
  ON d.department_id = mp.department_id
WHERE ua.account_status = 'ACTIVE'
  AND mp.mentor_status = 'AVAILABLE'
ORDER BY mp.full_name;
Implementation note: If a mentor has no current company, the LEFT JOIN still allows the profile to appear with a NULL 
company field.
Q03  Mentor skills and proficiency
Purpose: List a mentor’s registered skills and expertise level.
DBMS concepts: [C] JOIN across a many-to-many associative table.
SELECT
    mp.mentor_id,
    mp.full_name,
    s.skill_name,
    ms.proficiency_level,
    ms.years_experience,
    ms.is_primary_skill
FROM mentor_profile AS mp
JOIN mentor_skill AS ms
  ON ms.mentor_id = mp.mentor_id
JOIN skill AS s
  ON s.skill_id = ms.skill_id
WHERE mp.mentor_id = @mentor_id
ORDER BY ms.is_primary_skill DESC,
         s.skill_name;
Implementation note: The skill master is stored once; mentor_skill stores mentor-specific proficiency and experience.

Q06  Incomplete mentor profiles (NULL handling)
Purpose: Find available mentors whose company or professional fields are missing so an administrator can 
improve directory quality.
DBMS concepts: [C] NULL semantics, IS NULL, COALESCE.
SELECT
    mp.mentor_id,
    mp.full_name,
    mp.job_title,
    mp.current_city,
    mp.years_experience,
    CASE
      WHEN mp.company_id IS NULL THEN 'COMPANY_MISSING'
      WHEN mp.job_title IS NULL OR mp.job_title = '' THEN 'JOB_TITLE_MISSING'
      WHEN mp.biography IS NULL OR mp.biography = '' THEN 'BIO_MISSING'
      ELSE 'COMPLETE'
    END AS completeness_flag
FROM mentor_profile AS mp
WHERE mp.mentor_status = 'AVAILABLE'
  AND (
       mp.company_id IS NULL
       OR mp.job_title IS NULL OR mp.job_title = ''
       OR mp.biography IS NULL OR mp.biography = ''
  )
ORDER BY mp.mentor_id;
Implementation note: Use IS NULL, not = NULL. An empty string and SQL NULL are different values.
6. Discovery, relational operations and subqueries
The older mini-project asks for suitable alumni based on skill overlap. The newer blueprint adds domain 
relevance, relevant experience, career relevance, mentor quality and capacity. Neo4j supplies graph-based 
candidate paths, while MySQL revalidates eligibility, current capacity and quality before the final result. The 
following SQL queries support the relational side of discovery and reporting.
Q07  Mentor candidates by shared skills
Purpose: Find mentors sharing one or more skills with a student, ordered by number of distinct matching skills.
DBMS concepts: [B/C] JOIN, COUNT(DISTINCT), GROUP BY, ORDER BY.
SELECT

    COUNT(DISTINCT ss.skill_id) AS matched_skill_count,
    GROUP_CONCAT(DISTINCT s.skill_name
                 ORDER BY s.skill_name SEPARATOR ', ') AS matched_skills
FROM student_skill AS ss
JOIN mentor_skill AS ms

Q08  Mentors in a student-preferred domain
Purpose: Retrieve active mentors whose expertise matches at least one domain of interest for a student.
DBMS concepts: [B/C] JOIN, DISTINCT and many-to-many domain mapping.
SELECT DISTINCT
    mp.mentor_id,
    mp.full_name,
    md.domain_name,
    mde.expertise_level
FROM student_domain_interest AS sdi
JOIN mentor_domain_expertise AS mde
  ON mde.domain_id = sdi.domain_id
JOIN mentor_profile AS mp

ORDER BY md.domain_name,

Q09  Combine skill-based and domain-based mentor candidates (UNION)
Purpose: Combine two independent candidate retrieval routes without returning the same mentor twice.
DBMS concepts: [C] Set operation UNION; de-duplication.
SELECT
    candidates.mentor_id,
    mp.full_name,
    mp.job_title,
    mp.years_experience
FROM (
    SELECT ms.mentor_id
    FROM student_skill AS ss
    JOIN mentor_skill AS ms
      ON ms.skill_id = ss.skill_id
    WHERE ss.student_id = @student_id
 
    UNION
 
    SELECT mde.mentor_id
    FROM student_domain_interest AS sdi
    JOIN mentor_domain_expertise AS mde
      ON mde.domain_id = sdi.domain_id
    WHERE sdi.student_id = @student_id
) AS candidates
JOIN mentor_profile AS mp
  ON mp.mentor_id = candidates.mentor_id

SP02 - Create an atomic booking
The procedure uses MySQL as the final authority. It locks the student, availability and mentor rows; requires an 
active allocation under the current ER-aligned default; verifies mentor/account eligibility and capacity 
consistency; rejects time overlaps for either participant; then commits the booking, its scheduled session, the slot 
update and outbox event together. Existing allocated mentees are not rejected merely because the mentor is at 
the configured capacity limit.
A generated active_slot_key / unique index is recommended as a second line of defence. This procedure checks 
both student-side and mentor-side overlaps, not just the slot row. The current ER model makes allocation the

12. Triggers and audit enforcement
A trigger runs automatically when an INSERT, UPDATE or DELETE event occurs. The supplied Unit 2 material 
covers BEFORE / AFTER triggers, row-level execution, NEW and OLD values, and SIGNAL SQLSTATE for rejecting

procedures / application transactions for cross-table workflows.
Do not send external notifications from a trigger  Write a durable outbox row inside the same transaction; a 
worker delivers the notification after commit. Avoid duplicating the same outbox event in both a trigger and a stored 
procedure.

Q29  Request-to-allocation-to-session funnel using CTEs
Purpose: Measure request cohorts through acceptance, allocation and completed sessions.
DBMS concepts: [B/C] Common Table Expressions, aggregate counts, conditional aggregation.
WITH request_cohort AS (
    SELECT
        mr.request_id,
        mr.student_id,
        mr.status,
        mr.submitted_at,
        DATE_FORMAT(mr.submitted_at, '%Y-%m') AS cohort_month
    FROM mentorship_request AS mr
    WHERE mr.submitted_at >= @period_start
      AND mr.submitted_at <  @period_end
), allocation_by_request AS (
    SELECT
        ma.request_id,
        ma.allocation_id
    FROM mentor_allocation AS ma
), sessions_by_allocation AS (
    SELECT
        ms.allocation_id,
        COUNT(*) AS completed_sessions
    FROM mentorship_session AS ms
    WHERE ms.status = 'COMPLETED'
    GROUP BY ms.allocation_id
)
SELECT
    rc.cohort_month,
    COUNT(DISTINCT rc.request_id) AS requests_submitted,
    COUNT(DISTINCT CASE WHEN rc.status = 'ACCEPTED'
                        THEN rc.request_id END) AS requests_accepted,
    COUNT(DISTINCT abr.allocation_id) AS allocations_created,
    COALESCE(SUM(sba.completed_sessions), 0) AS completed_sessions
FROM request_cohort AS rc
LEFT JOIN allocation_by_request AS abr
  ON abr.request_id = rc.request_id
LEFT JOIN sessions_by_allocation AS sba
  ON sba.allocation_id = abr.allocation_id
GROUP BY rc.cohort_month
ORDER BY rc.cohort_month;

Q30  Rank mentors within each mentorship domain
Purpose: Rank mentors by average student review rating within each expertise domain.
DBMS concepts: [B/C] CTE + window function RANK() OVER(PARTITION BY ...).
WITH mentor_ratings AS (
    SELECT
        mr.mentor_id,
        COUNT(*) AS review_count,
        AVG(mr.rating) AS average_rating
    FROM mentor_review AS mr
    GROUP BY mr.mentor_id
), domain_scores AS (
    SELECT
        md.domain_id,
        md.domain_name,
        mp.mentor_id,
        mp.full_name,
        COALESCE(mr.review_count, 0) AS review_count,
        mr.average_rating,
        mp.years_experience
    FROM mentor_domain_expertise AS mde
    JOIN mentorship_domain AS md
      ON md.domain_id = mde.domain_id
    JOIN mentor_profile AS mp
      ON mp.mentor_id = mde.mentor_id
    LEFT JOIN mentor_ratings AS mr
      ON mr.mentor_id = mp.mentor_id
)
SELECT
    domain_name,
    mentor_id,
    full_name,
    review_count,
    ROUND(average_rating, 2) AS average_rating,
    years_experience,
    RANK() OVER (
        PARTITION BY domain_id
        ORDER BY average_rating DESC,
                 years_experience DESC
    ) AS domain_rank
FROM domain_scores
WHERE review_count >= 3
ORDER BY domain_name, domain_rank;
Implementation note: RANK() gives tied values the same rank. Use ROW_NUMBER() where a unique deterministic ordinal is 
required. The review-count filter avoids ranking mentors on a single review.

14.4 Query-writing practices

Filter on indexed raw columns where possible. Avoid wrapping an indexed timestamp in DATE() in the 
WHERE predicate when a timestamp range expresses the same requirement.

Use DISTINCT only when duplicate elimination is part of the requirement; unnecessary DISTINCT can add 
sorting or temporary-table work.

Aggregate child tables before joining several one-to-many relationships, or counts can be multiplied by join 
fan-out.

Select only fields needed by the endpoint or report; avoid SELECT * in public APIs.

Use keyset pagination for deep result sets where appropriate; OFFSET pagination becomes more expensive as 
offsets grow.

Measure with representative data volumes. The earlier mini-project estimates 500–2,000 students, 1,000–5,000 
alumni, thousands of skill associations and up to 10,000 sessions; scale synthetic data if needed for 
optimisation demonstrations.

Do not use a cached result to make a booking decision. Re-read and validate current slot state inside the 
MySQL transaction.

15.2 Why locking matters for booking
A simple “SELECT available slot” followed by INSERT is unsafe when two students act at nearly the same time. 
The slot row must be locked and revalidated. Also check student-side overlaps and mentor-side overlaps. A 
unique constraint on the active slot key acts as a second line of defence, while row locks serialize the business 
operation.

15.3 Transactional outbox pattern
The request, booking, session and review routines insert an outbox event in the same MySQL transaction as the 
business write. A background worker reads committed outbox events, sends in-app/email notifications as 
configured, updates Neo4j projections and invalidates relevant Redis recommendation/profile cache keys. Use a 
stable event identifier and idempotent worker operations to make retries safe.
