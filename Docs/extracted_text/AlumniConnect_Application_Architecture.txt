1. Purpose and architectural direction
This document defines how the AlumniConnect web application is divided into user-facing interfaces, backend 
business modules and database systems. It translates the supplied project blueprint into an implementation-oriented 
architecture that can be built and demonstrated as a DBMS mini-project.
1.1 Product boundary
AlumniConnect connects college students with alumni who can provide career guidance, mentorship and mock interviews. 
Students maintain profiles, discover suitable mentors, submit requests, book appointments and review completed sessions. 
Alumni maintain professional profiles, publish availability, accept requests and record session outcomes. Administrators 
manage users, reference data and platform-level reports.
1.2 Core architectural decision
Recommended architecture: modular monolith + polyglot persistence
Deploy one FastAPI backend application. Organise it into independent business modules, but keep coordinated business 
operations in one application and one authoritative MySQL database. Use Redis and Neo4j only for their specialised access 
patterns. The API boundary of FastAPI is the logical API Gateway; it does not need to be a separately deployed gateway 
service.
1.3 Why this is the right fit
Booking, mentorship allocation and session updates involve related records that should be committed together in SQL 
transactions.
A database-per-microservice design would add distributed consistency and deployment work without a project-scale 
benefit.
Clear module boundaries preserve separation of responsibilities and make the backend easier to test and extend.
The design still demonstrates relational SQL, ACID transactions, caching, key-value data structures and graph 
traversal.
1.4 Design principles
Principle
Meaning in AlumniConnect
Single source of truth
MySQL owns identities, profiles, requests, allocations, availability, bookings, sessions, feedback and 
audit/notification records.
Specialised persistence
Redis accelerates reads and stores temporary state; Neo4j supports relationship-oriented 
recommendations; vector search is optional.
Business logic in modules
Modules own domain rules and coordinate repository/database access; routers should remain thin.
Transactional correctness
Critical state changes are validated and committed atomically in MySQL/InnoDB.
Asynchronous side effects
Outbox events drive notifications, graph projection updates and cache invalidation after the MySQL 
commit.
Important distinction
Redis and Neo4j are not replicas that can overrule MySQL. Redis values are disposable/rebuildable. Neo4j is an eventually 
consistent graph projection. MySQL is authoritative whenever data disagrees.

2.2 API Gateway interpretation
The API Gateway is a logical boundary, not a required additional service. In this design, the FastAPI application exposes 
the public API and performs routing, authentication, authorization, input validation and response formatting. Internal 
modules are called by the routers/application services; the frontend does not call database servers directly.
2.3 Request path at a glance
1. A user performs an action in the Student, Mentor or Administrator portal.
2. Next.js sends an HTTPS request to a FastAPI endpoint with the user identity/session context.
3. The API boundary authenticates the caller and checks the role and resource-level permission.
4. The responsible backend module applies business rules and chooses the required database access pattern.
5. The API returns a response; asynchronous work is processed from the outbox after the main SQL transaction 
commits.

5. How modules collaborate
A module boundary separates responsibility, but a complete user action often crosses several modules. The orchestrating 
application service coordinates the sequence and defines where the transaction begins and ends.
5.1 Student requests a mentor
1. Student Discovery page sends skill, domain, experience and career-goal filters to the Mentor Discovery API.
2. Discovery uses Neo4j for relationship-based candidate generation and MySQL for current eligibility, capacity and 
quality checks. Redis may serve a valid cached recommendation result.
3. The frontend displays ranked mentor cards with reasons such as shared skills, domain relevance and relevant industry 
experience.
4. When the student selects a mentor, the Mentorship Requests module re-validates the selected mentor and creates a 
Pending request in MySQL.
5. The same SQL transaction records an outbox event. After commit, the worker delivers a request notification to the 
mentor.
Request states
Pending -> Accepted / Rejected / Cancelled. Rejected and cancelled requests remain in history for reporting; they are not 
deleted merely because the request did not lead to an allocation.
5.2 Mentor accepts or rejects a request
1. The mentor opens the pending request and submits an accept/reject action.
2. The backend verifies that the request is still Pending, that the caller is the assigned mentor and that the mentor can 
accept another allocation.
3. On acceptance, MySQL creates the allocation and changes the request status inside one transaction; constraints and 
duplicate-active-allocation checks protect integrity.
4. An outbox record is inserted in the same transaction. After commit, the student receives the outcome notification.
5. On rejection, the request status is updated and retained in history; no allocation is created.
5.3 Availability and bookings
Availability is published by the mentor and stored in MySQL. The student interface can display a cached or previously 
fetched availability view, but the booking command always re-reads and validates the current slot in MySQL before 
confirming it.
5.4 Offline session recording
A booking is the planned appointment; a mentorship session is the actual meeting and its outcome. The mentor records 
whether the meeting was completed, cancelled or marked as no-show, plus discussion topics, skills assessed, 
observations, improvement areas and next steps. The system preserves the history of the session.
5.5 Feedback and mentor review
Session feedback captures structured comments from an actual participant (for example communication, helpfulness, 
preparation and notes). A mentor review is a student rating/review of the mentor after a completed session. These are 
separate concepts because they answer different reporting questions.

6.3 Core integrity rules
Use primary keys to identify each record and foreign keys to protect relationships between accounts, profiles, requests, 
allocations, bookings, sessions and feedback.
Use unique constraints to prevent duplicate identities and duplicate ownership of a single availability slot.
Use status constraints / controlled application transitions so requests and sessions cannot jump to invalid states.
Only participants can access or submit session feedback; one student can submit at most one mentor review per 
session.
A review must reference a valid completed session; feedback must not be accepted before the meeting has occurred.
Retain rejected/cancelled request history and session history rather than deleting business history.
Schema note
The entities above describe the proposed conceptual model. Exact column names, data types, check constraints, indexes and 
physical table decomposition should be finalised during relational schema design and normalization.

Cache-aside read pattern
1. The API checks Redis for the requested profile or recommendation key.
2. On a cache hit, the application returns the cached display data after normal authorization checks.
3. On a cache miss, the application reads MySQL (or invokes the appropriate discovery path), builds the response and 
writes a cache entry with a TTL.
4. When the authoritative profile or skill changes, the update path invalidates relevant profile and recommendation keys. 
TTL is a safety net, not the only invalidation plan.
Never cache booking authority
Do not use Redis to decide whether a slot is free. Do not let a cache hit bypass MySQL authorization, availability validation, 
overlap checks or booking transaction logic.

8. Cross-database consistency and event processing
The platform deliberately accepts different consistency roles for its stores: MySQL is strongly authoritative for business 
state; Redis is disposable cache/temporary state; Neo4j is an eventually consistent recommendation projection. This is 
safer than attempting an uncoordinated write to every database during a user request.
8.1 Transactional outbox pattern
When a MySQL business operation also requires a notification, graph update or cache invalidation, the application inserts 
an outbox event inside the same MySQL transaction as the business change. A worker reads committed events later and 
performs the secondary side effects.
Figure 4. A profile update and its outbox event commit together. Secondary stores are updated asynchronously.

8.3 Reliability requirements for the worker
Process only committed outbox rows; do not publish a side effect before the SQL transaction commits.
Use stable event identifiers and idempotent upsert/invalidation operations so retries do not create duplicates.
Track pending, processed and failed attempts; retain enough error detail to investigate failures.
Retry transient errors with bounded backoff; do not silently discard a failed event.
Treat a delayed graph projection as a recommendation freshness issue, not as permission to skip MySQL validation.
Consistency rule
If Neo4j or Redis disagrees with MySQL, the MySQL result wins. A candidate returned by Neo4j may be removed by MySQL 
eligibility checks. A stale availability cache must never confirm a booking.

transaction.

9.1 Checks before confirmation
The mentor availability slot still exists and is available at the time of the transaction.
The student does not already have an overlapping confirmed booking.
The mentor has not exceeded their mentorship or scheduling capacity.
The referenced request or allocation is valid for the requested meeting.
The submission is not a duplicate retry (idempotency key / uniqueness protection).
9.2 Transaction responsibilities
Transaction stage
Expected database action
Begin
Start one InnoDB transaction for the booking use case.
Read and lock
Re-read the target availability row using a transaction-safe locking strategy; do not rely on cached data.
Validate
Check slot state, allocation, mentor capacity, student overlap and duplicate submission.
Write
Insert the booking, update the slot state, create the planned session record if that is part of the chosen model, and 
insert the relevant outbox event.
Commit / rollback
Commit all related changes together. If a validation or write fails, roll back so no partial booking remains.
Respond
Return a confirmed booking or a conflict/unavailable response. The frontend refreshes the schedule from the API.
9.3 Concurrency safeguards
Use database uniqueness and transactional locking to prevent two requests from claiming the same slot. Also protect 
against overlapping appointments on the student side; locking only the mentor slot is not sufficient. The final schema 
should include the relevant unique keys and supporting indexes, and the booking service should test concurrent 
submissions under the selected InnoDB isolation/locking strategy.
Required concurrency demonstration
Run two simultaneous booking attempts for one slot. Exactly one must commit; the other must receive a conflict/unavailable 
result. Repeat with one student attempting two overlapping appointments.

Separating the two prevents a planned meeting from being mistaken for a completed mentoring interaction. A booking can

10.2 Feedback and review rules
A session cannot receive feedback before it has taken place.
Only the actual student and mentor participants can submit feedback for that session.
One student can submit at most one mentor review per session.
A mentor review must reference a valid completed session.
Review history should not be silently overwritten; maintain auditable changes or append-only history where required.

10.4 Notification processing sequence
1. A business module writes the domain change and outbox event in the same MySQL transaction.
2. After commit, a worker polls or claims pending outbox events.
3. The worker creates the notification record and invokes the configured delivery adapter.
4. Success/failure status is persisted so the task can be retried or inspected.
5. The user sees the notification through the web application; the authoritative notification record remains in MySQL.

12.1 Query-processing path for a screen
For example, when the administrator opens a mentor analytics report, the FastAPI analytics service issues an SQL query. 
The DBMS scans and parses the SQL, validates referenced names, creates an internal query representation, chooses an 
execution plan through query optimization, and executes that plan to return the result. The application then formats the 
result for the dashboard.

and a database server accessible through the middle tier. The Unit 3 slides describe scanning, parsing, validation, 
query-tree/query-plan generation and query optimization. The proposed application architecture uses those ideas directly.

13. Security, reliability and operational boundaries
The blueprint establishes roles and permissions as part of Identity and Access. The following implementation controls are 
recommended to make that boundary reliable in a web application.
13.1 Access control
Control
Implementation responsibility
Role-based access
Assign Student, Mentor and Administrator roles; each API operation declares which roles may invoke it.
Resource ownership
Verify the caller owns the profile/booking/feedback record or is an actual participant in the relevant request/session.
Least privilege
Expose public mentor directory fields separately from private account and contact information.
Server-side enforcement
Repeat permission checks in FastAPI even when Next.js hides controls or redirects users.
Sensitive credentials
Store password hashes, never plaintext passwords; keep secrets and database credentials outside source code.
13.2 Reliability boundaries
Failure / risk
Expected behaviour
Redis unavailable
Continue with MySQL-backed reads where practical; cache loss must not corrupt business state.
Neo4j unavailable
Temporarily degrade discovery (for example, use supported SQL filters) or return a controlled unavailable 
response; do not invent eligibility.
Worker unavailable
Committed business updates remain valid; outbox events stay pending until processing resumes.
Duplicate client retry
Use idempotency/unique constraints so repeated submission does not create duplicate bookings or allocations.
Concurrent slot request
Only one transaction can claim the slot; losing request receives conflict/unavailable response.
Stale recommendation
Re-check current mentor eligibility and capacity in MySQL before a request/allocation/booking decision.
13.3 Observability
Log request correlation ID, actor ID, module, operation outcome and duration; do not log passwords or secrets.
Track booking conflicts, transaction rollbacks, cache hit/miss rate, recommendation latency and outbox backlog.
Provide a way to inspect failed outbox events and retry them safely.
Keep audit records for important account, request, allocation, booking, session and review status changes.

15.1 Architecture acceptance checklist
There is one FastAPI application boundary; backend capabilities are modules, not separately deployed microservices.
The frontend never connects directly to MySQL, Redis or Neo4j.
All authoritative identity, profile, request, allocation, scheduling, booking, session, feedback and audit records are in MySQL.
Redis is used for caches/temporary state and never decides slot availability.
Neo4j stores a relationship projection and can be rebuilt from authoritative data/events.
Critical writes use MySQL transactions; booking has uniqueness, lock/check and rollback protection.
Outbox events are inserted in the same SQL transaction as their business change and processed asynchronously.

Appendix B. Explicit design assumptions
The REST route catalogue, package layout, deployment units, security controls and operational metrics are proposed 
implementation details added to make the blueprint actionable; they are not claimed to be existing code or a finalized API 
contract.
The exact booking lock strategy and the physical constraints needed to prevent time-interval overlap depend on the final 
schema, indexes and InnoDB isolation level. The architectural requirement is that MySQL performs the final serialized 
validation and commit.
The notification delivery channel is left as an adapter because the supplied blueprint defines notification events and outbox 
processing but does not mandate a specific email/SMS/push provider.
The graph projection is eventually consistent; recommendations can be slightly stale. Critical allocation and booking decisions 
must be re-validated in MySQL.
Vector search is optional Phase 2 scope, not a prerequisite for the core application.
Appendix C. Short glossary
Term
Meaning in this design
Modular monolith
One deployable backend containing clearly separated business modules.
Polyglot persistence
Using multiple database types because each suits a different access pattern.
System of record
The authoritative database that owns the correct business value; MySQL here.
Cache-aside
Application checks cache first, reads the source on a miss and stores a temporary copy.
Projection
A derived representation built from authoritative records for a specialized query pattern.
Transactional outbox
A durable event row written in the same SQL transaction as the business update; a worker publishes it later.
Idempotency
Repeated execution of the same request produces no duplicate business effect.
Eventual consistency
A secondary store may lag briefly but converges after asynchronous updates are processed.
