1. Executive design summary
AlumniConnect is modelled as a relational system of record with a normalized MySQL database. It stores account 
identity, role-specific profiles, skills and domains, mentorship requests, recommendations, allocations, availability, 
bookings, sessions, feedback, reviews, notifications and audit history.
Design area
Decision
Primary relational store
MySQL 8.x / InnoDB owns authoritative identities and business records.
Identity
One UserAccount represents one login identity. StudentProfile and MentorProfile extend that 
identity.
Many-to-many data
Use associative relations such as StudentSkill, MentorSkill, StudentDomainInterest and 
MentorDomainExpertise.
Mentorship lifecycle
Keep MentorshipRequest separate from MentorAllocation. An accepted request can create at most 
one allocation.
Scheduling
Keep MentorAvailability, Booking and MentorshipSession separate. A booking records a plan; a 
session records what actually happened.
Operational history
Use NotificationOutbox for reliable event delivery and AuditLog for append-only change history.
Polyglot persistence
Redis holds rebuildable cache / temporary values. Neo4j holds a graph projection for discovery. 
Neither replaces MySQL as source of truth.
Normalization target
Aim for 3NF, and BCNF where the business dependencies support it, while preserving lossless joins 
and preferably dependency preservation.
Core relational domains
Domain
Main relations
Identity and organization
Role, UserAccount, StudentProfile, MentorProfile, Department, Company
Skills and expertise
Skill, StudentSkill, MentorSkill, MentorshipDomain, StudentDomainInterest, 
MentorDomainExpertise
Discovery and allocation
MentorshipRequest, RecommendationRun, RecommendedMentor, MentorAllocation
Scheduling and sessions
MentorAvailability, Booking, MentorshipSession, SessionSkillAssessment
Feedback and operations
SessionFeedback, MentorReview, Notification, NotificationOutbox, AuditLog
WHY THIS DESIGN WORKS
It separates facts that change at different rates and have different meanings. A profile is not a request; a request is not 
an allocation; a booking is not a completed session; and a notification event is not the same thing as a user inbox 
notification.

2. Scope, assumptions and design decisions
The following decisions turn the conceptual model and Business Rules Catalogue into a concrete logical schema. [B] 
marks a blueprint/source-aligned rule; [R] marks an implementation recommendation added where the sources leave 
a choice open; [T] marks a technical enforcement mechanism. The newest Business Rules Catalogue is used to resolve 
lifecycle vocabulary, while deviations made for normalization are explicitly explained.
2.1 Source alignment and important reconciliations
Topic
Decision used in this relational specification
Reason / source reconciliation
Allocation lifecycle
Use ACTIVE -> ENDED.
The current Business Rules Catalogue uses ACTIVE and ENDED. 
Older draft vocabulary such as COMPLETED / TERMINATED is 
not used in the canonical schema.
Booking eligibility
BOOKING.allocation_id is mandatory and must 
reference an ACTIVE allocation.
The core workflow and current booking rules require an 
accepted allocation. The conceptual ER model marks this link as 
optional only for a possible alternate appointment mode; that 
optional mode is excluded from this core Release 1 schema.
Allocation participants
Store request_id once; derive student and mentor 
through MENTORSHIP_REQUEST.
The conceptual entities are traceable through the originating 
request. Repeating student/mentor IDs in 
MENTOR_ALLOCATION creates redundant facts and is not 
needed for normalized storage.
Booking participants 
and time
Store allocation_id and availability_id; derive 
participants and slot times through joins.
The Business Rules Catalogue includes a query-oriented sample 
that repeats student_id, mentor_id, start_at and end_at in 
BOOKING. This specification omits those duplicates in the 
normalized base relation; a view can expose them. If snapshots 
are required, label them as immutable booking-time snapshots 
and document the controlled denormalization.
Availability vocabulary
Use OPEN, BOOKED, BLOCKED and EXPIRED.
The current Business Rules Catalogue describes a slot as OPEN 
before reservation and BOOKED after confirmation; BLOCKED 
and EXPIRED are recommended non-bookable states.
Notification data
Store one outbox event, then fan out into one or 
more NOTIFICATION rows.
This preserves the conceptual 1-to-many Outbox-to-Notification 
relationship. Do not write one outbox row per recipient unless 
the team deliberately changes the event model.
Business event log
Use AUDIT_LOG for actor/action history and 
NOTIFICATION_OUTBOX for asynchronous 
delivery.
The business-rule SQL examples mention business_event_log, 
but the conceptual entity catalogue contains Audit Log and 
Notification Outbox. This schema keeps those responsibilities 
separate without adding a duplicate event table.
NORMALIZATION DECISION
A logical model should not copy student, mentor, slot-time or company-description attributes into every child row 
when those values are already determined through a parent key. Use joins or privacy-safe views for display. 
Denormalize only after measuring a real query bottleneck and documenting how the duplicated value stays 
synchronized.
Assumption
Proposed rule
A1. One primary role [R]
Each UserAccount has one primary Role through role_id. A user may have zero or one StudentProfile and 
zero or one MentorProfile, but Release 1 assigns one primary operating role. If dual-role users are 
required, replace role_id with a UserRole bridge and define profile-role consistency. [ER model R01-R03]
A2. Targeted request [B]
A MentorshipRequest identifies one student, one target mentor and one mentorship domain/objective. 
Open requests not addressed to a mentor are outside this schema.
A3. One allocation per 
request [B]
A request can result in zero or one MentorAllocation. UNIQUE(request_id) enforces this cardinality.

Assumption
Proposed rule
A4. Allocation participant 
derivation [R]
MentorAllocation stores request_id, lifecycle fields and allocation metadata. Student and mentor are 
derived from the originating request, avoiding duplicate facts.
A5. Recommendation 
history [B/R]
Each RecommendationRun belongs to one student. A mentor appears at most once per run and each rank 
position is unique within that run. Scores and explanations are retained per run.
A6. Availability identity 
[B/R]
A mentor may publish many slots. Exact duplicate intervals are prohibited by UNIQUE(mentor_user_id, 
starts_at, ends_at); overlapping OPEN slots require a locked procedure because UNIQUE cannot detect 
interval overlap.
A7. Booking eligibility [B/R]
Every core Release 1 booking references one ACTIVE allocation and one availability slot owned by that 
allocation mentor. Booking participants and interval are derived through Allocation/Request and 
Availability.
A8. Booking history and 
slot reuse [B/R]
Cancelled bookings remain in history. A generated active_availability_id is non-NULL only for 
CONFIRMED bookings, allowing one active booking per slot while retaining cancelled rows. Reopening a 
slot after cancellation is policy-controlled.
A9. Participant overlap [B]
A student and a mentor must each have no other CONFIRMED booking overlapping the requested half-
open interval [start, end). A transaction locks participant profile rows before checking.
A10. Session creation [B/R]
A confirmed booking creates at most one SCHEDULED MentorshipSession; the implementation inserts it 
in the booking transaction. Cancelled bookings need not have a session.
A11. Feedback cardinality 
[B/R]
SessionFeedback may be submitted by either actual participant after a completed session; enforce at most 
one row per participant per session. MentorReview is a separate student-authored rating, at most one per 
completed session.
A12. Controlled 
vocabularies [R]
Roles, skills and mentorship domains are reference data. Skill and domain labels are canonicalized and 
unique within the project scope.
A13. Historical snapshots 
[R]
A request may preserve career_goal_snapshot at submission. This is a deliberate historical snapshot, not a 
live copy of StudentProfile.career_goal.
A14. History retention 
[B/R]
Requests, allocations, bookings, sessions, reviews and audit evidence are status-changed or moderated 
rather than physically deleted in normal operations.
A15. Event fan-out [B/R]
NotificationOutbox stores a durable domain event. One event can create multiple Notification inbox rows, 
one per recipient; dedupe keys prevent duplicate creation/delivery.
A16. Department key [R]
department_code is treated as unique within the single-institution project. For multi-institution use, 
replace UNIQUE(department_code) with UNIQUE(institution_id, department_code).
CONFIRM BEFORE BUILDING
Confirm whether accounts can have multiple roles, whether a student can have several active mentors, whether 
cancelled slots are reusable, and whether feedback is one-way or two-way. These choices affect uniqueness constraints 
and lifecycle rules.

3. Relational modelling conventions
Notation
Meaning
PK
Primary key: minimal attribute set identifying one row.
FK
Foreign key: attribute(s) referencing a primary or alternate unique key in another relation.
UQ
Unique alternate/candidate key enforced with a UNIQUE constraint.
NN
NOT NULL; a value is mandatory.
NULL
Optional value; only use where the business lifecycle permits absence.
(A, B)
Composite key formed by more than one attribute.
1:N
One parent row may relate to many child rows.
0..1
Optional zero-or-one participation.
JSON
Opaque operational payload; do not use JSON arrays as a substitute for relational bridge tables.
Key terminology

Superkey: any attribute set that uniquely identifies each legal tuple. A superkey may contain extra attributes.

Candidate key: a minimal superkey. Removing any attribute causes uniqueness to fail.

Primary key: the candidate key selected as the main row identifier.

Alternate key: a candidate key not selected as the primary key; normally enforced using UNIQUE.

Prime attribute: an attribute that belongs to at least one candidate key. A non-prime attribute belongs to no 
candidate key.

Functional dependency X -> Y: when two valid rows agree on X, they must also agree on Y.

Full functional dependency: Y depends on the whole determinant X; no proper subset of X determines Y.

Partial dependency: some proper subset of a composite key determines a non-prime attribute.

Transitive dependency: key -> intermediate non-key -> another non-prime attribute.
Naming and datatype conventions
Convention
Recommendation
Identifiers
BIGINT UNSIGNED AUTO_INCREMENT for surrogate IDs; bridge tables use composite primary keys.
Email
VARCHAR(254), NOT NULL, UNIQUE; normalize case before storage or use a consistent collation.
Timestamps
DATETIME(6) stored consistently in UTC; application converts for display.
Amounts / scores
Use DECIMAL rather than FLOAT for values requiring predictable decimal precision.
Boolean flags
BOOLEAN / TINYINT(1), with explicit defaults and CHECK where supported.
Status
Use an ENUM or a lookup table; status values must be treated as finite lifecycle vocabularies.
Long-form notes
TEXT; split into separate fields only when they have independent meaning or querying needs.
JSON
Use only for flexible snapshots / event payloads, not lists of skills or normalized attributes.

5.4 Armstrong axioms and useful inference rules
Armstrong axioms are sound and complete rules for reasoning about functional dependencies. They help derive F+ 
(the closure of an FD set), prove whether an attribute set is a key, and remove redundant dependencies when finding 
a minimal cover.
Rule
Statement
Interpretation
Reflexivity
If Y is a subset of X, then X -> Y.
A set determines any subset of itself.
Augmentation
If X -> Y, then XZ -> YZ.
Adding the same attributes to both sides preserves an FD.
Transitivity
If X -> Y and Y -> Z, then X -> Z.
Dependencies can be chained.
Decomposition
If X -> YZ, then X -> Y and X -> Z.
A multi-attribute right side can be split.
Union
If X -> Y and X -> Z, then X -> YZ.
Dependencies with the same determinant can be combined.
Pseudotransitivity
If X -> Y and WY -> Z, then WX -> Z.
A useful derived rule for longer FD chains.
5.5 Minimal cover (canonical cover)
A minimal cover is an equivalent FD set in which every right-hand side has one attribute, no left-hand-side attribute is 
extraneous, and no dependency is redundant. A practical procedure is: (1) split multi-attribute right sides; (2) test and 
remove extraneous determinant attributes using closure; (3) remove each FD in turn if the remaining set still implies 
it.
Example: F = { (student_user_id, skill_id) -> proficiency_level, years_experience, added_at }
Split RHS: { (student_user_id, skill_id) -> proficiency_level,
             (student_user_id, skill_id) -> years_experience,
             (student_user_id, skill_id) -> added_at }
No determinant attribute is extraneous under the stated business rule: neither
student_user_id nor skill_id alone determines any association-specific attribute.
No FD is redundant. This is a minimal cover for the stated relation.
IMPORTANT
A UNIQUE constraint is not just a performance index: it asserts a business dependency. Do not add UNIQUE(email), 
UNIQUE(company_name) or UNIQUE(mentor_id, skill_id) unless the underlying business rule actually requires it.

6. Candidate-key derivation and attribute closure
Attribute closure X+ is the set of all attributes functionally determined by X under the stated FD set. If X+ contains 
every attribute of a relation, X is a superkey; if no proper subset of X is a superkey, X is a candidate key.
Example 1 - StudentSkill composite key
Relation: STUDENT_SKILL(student_user_id, skill_id, proficiency_level, years_experience, added_at). Proposed FD set:
(student_user_id, skill_id) -> proficiency_level, years_experience, added_at
Closure: {student_user_id, skill_id}+ = {student_user_id, skill_id, proficiency_level, years_experience, added_at}. 
Neither {student_user_id}+ nor {skill_id}+ determines the association-specific proficiency. Therefore the pair is a 
minimal superkey and the candidate key.
Example 2 - UserAccount alternate key
user_id -> role_id, email, password_hash, display_name, account_status, created_at, updated_at
email   -> user_id, role_id, password_hash, display_name, account_status, created_at, updated_at
If email is declared UNIQUE and NOT NULL, both user_id and email are candidate keys. user_id is selected as the 
primary key; email is the alternate key. If email can be changed, the surrogate PK remains stable while the unique 
rule still prevents duplicate active identities.
Example 3 - RecommendedMentor candidate keys
recommendation_id -> run_id, mentor_user_id, rank_position, score, eligibility_status, explanation_text
(run_id, mentor_user_id) -> rank_position, score, eligibility_status, explanation_text
(run_id, rank_position) -> mentor_user_id, score, eligibility_status, explanation_text  [if rank is unique]
The design chooses recommendation_id as the primary key for convenient references. The two composite unique 
constraints protect business uniqueness within each recommendation run.
Example 4 - Allocation request uniqueness
allocation_id -> request_id, allocation_status, allocated_at, ended_at, termination_reason
request_id -> allocation_id, allocation_status, allocated_at, ended_at, termination_reason  [UNIQUE(request_id)]
A request can be accepted only once into a single allocation. The unique request_id constraint is the database-level 
expression of the 1:0..1 request-to-allocation rule. Participant IDs are intentionally derived via the request rather than 
stored again.
Example 5 - Booking key and why the availability FK is not a global candidate key
booking_id -> allocation_id, availability_id, booking_status, booked_at, cancelled_at, cancellation_reason
idempotency_key -> booking_id and remaining attributes  [UNIQUE, NOT NULL]
active_availability_id -> booking_id  [only for CONFIRMED rows]
A cancelled booking remains in history and a slot may later be booked again if policy permits. Therefore 
availability_id does not uniquely identify every historical BOOKING row. The nullable generated active_availability_id 
is a partial uniqueness guard for confirmed rows, not a candidate key for the entire relation.
Example 6 - Mentor review alternate candidate key
review_id -> session_id, rating, review_text, submitted_at
session_id -> rating, review_text, submitted_at  [UNIQUE(session_id)]

How to compute a closure in practice
1.
Start with X+ = X.
2.
For each FD Y -> Z, if Y is contained in the current closure, add Z.
3.
Repeat until no new attributes can be added.
4.
Compare the resulting closure with the full relation heading.
5.
Test minimality by removing one attribute at a time from X.
IMPORTANT
A list of sample rows cannot prove an FD. The team must establish the business rule (for example, “email uniquely 
identifies an account”) and enforce it with a UNIQUE constraint or other mechanism.

7. Normalization walkthrough: 1NF to BCNF, with 4NF/5NF 
context
Normalization analyzes relation schemas using functional dependencies and keys to reduce unnecessary redundancy 
and avoid insertion, update and deletion anomalies. The course material emphasizes 1NF, 2NF, 3NF and BCNF, with 
lossless join and dependency preservation as additional design requirements.
7.1 Start with an unsafe combined relation
Suppose a first draft stores a student, mentor, skills, domain, request, booking, meeting and review in one wide 
relation. It may contain repeated values such as “Python, SQL, Docker”, nested booking histories or several feedback 
entries in one record. This is not a good relational design.
Problem
Anomaly created
Repeated skill lists in one field
Filtering, joining and validating each skill becomes unreliable; violates atomicity.
Mentor name copied into every skill row
Changing a mentor name requires many row updates; update anomaly.
Company name repeated with each 
mentor
Company data changes can produce inconsistent copies.
Booking columns mixed with session 
outcome
A planned appointment and the actual meeting become indistinguishable.
Feedback stored as a list or repeated 
columns
Cannot reliably enforce one feedback per participant or query each response 
independently.
7.2 First Normal Form (1NF)
1NF requires every attribute value to be atomic for the chosen domain and disallows repeating groups, multi-valued 
attributes and nested relations. Each row-column intersection holds one value.
UNNORMALIZED: StudentProfile(user_id, name, skills = "Python, SQL, Docker")
1NF:          StudentProfile(user_id, name, ...)
              StudentSkill(user_id, skill_id, proficiency_level, ...)

Move each student-skill pair to a separate StudentSkill row. Do the same for mentor skills and domain 
interests/expertise.

Move each assessed skill for a session to SessionSkillAssessment rather than storing a comma-separated list.

Keep one feedback submission per row; do not place a collection of feedback objects in a column.
7.3 Second Normal Form (2NF)
2NF requires 1NF and every non-prime attribute to be fully functionally dependent on every candidate key. A relation 
with a single-attribute candidate key cannot have a partial dependency on a proper subset of that key.
Illustrative unsafe relation: MENTOR_SKILL_DETAIL(mentor_id, skill_id, mentor_name, company_id, skill_name, 
proficiency_level). Its candidate key is (mentor_id, skill_id). The following dependencies hold under this example:
mentor_id -> mentor_name, company_id
skill_id  -> skill_name
(mentor_id, skill_id) -> proficiency_level
company_id -> company_name  [if company_name had been included]
mentor_id -> mentor_name and skill_id -> skill_name are partial dependencies because each depends on only part of 
the composite key. Decompose into MentorProfile, Company, Skill and MentorSkill. Keep proficiency_level in 
MentorSkill because it describes the mentor-skill pair.

7.4 Third Normal Form (3NF)
The general 3NF test is: for every non-trivial FD X -> A, either X is a superkey or A is a prime attribute. Informally, non-
key attributes should depend on the key, the whole key and nothing but the key.
UNSAFE: StudentDetail(user_id, student_number, department_id, department_code, department_name, programme)
FDs:    user_id -> student_number, department_id, programme
        student_number -> user_id, department_id, programme  [if unique]
        department_id -> department_code, department_name
DECOMPOSE:
        StudentProfile(user_id, student_number, department_id, programme, ...)
        Department(department_id, department_code, department_name, ...)
department_id -> department_name is a transitive dependency from the student key through department_id. Store 
department facts once in Department and reference them by a foreign key.
7.5 Boyce-Codd Normal Form (BCNF)
BCNF is stronger than 3NF. For every non-trivial FD X -> A, X must be a superkey. Some relations can satisfy 3NF but 
fail BCNF when a non-superkey determinant determines a prime attribute. The actual FD set must be checked before 
claiming BCNF.
ALUMNICONNECT TARGET
The proposed relations are designed to be in 3NF and generally BCNF under the stated business dependencies. This is a 
design target, not a mathematical proof for unknown future rules. Re-check BCNF whenever a new uniqueness rule or 
cross-attribute dependency is introduced.

8. Lossless join, dependency preservation and integrity
8.1 Lossless (non-additive) join
A decomposition is lossless when joining the decomposed relations recreates exactly the original valid relation 
without generating spurious tuples. For a binary decomposition R into R1 and R2, the common attributes must 
functionally determine all attributes in at least one side under F+ (the lossless binary decomposition test taught in Unit 
3).

StudentProfile.department_id references Department.department_id. Joining a student profile to its department by 
that key returns the department determined by the FK.

MentorSkill joins to MentorProfile by mentor_user_id and to Skill by skill_id. Joining through the full bridge key 
reconstructs the mentor-skill association without inventing combinations.

Do not join a relation using a descriptive attribute such as company_name or skill_name if it is not guaranteed 
unique; that can create duplicate or spurious combinations.
8.2 Dependency preservation
A decomposition is dependency-preserving when each FD can be checked in an individual resulting relation without 
requiring an expensive join. This is desirable because unique constraints and checks can be applied locally. The Unit 3 
material emphasizes that lossless join is essential and dependency preservation is desirable; when BCNF 
decomposition loses a dependency, preserve losslessness and document the trade-off.
8.3 Integrity constraints to implement
Constraint class
AlumniConnect rule / example
Entity integrity
Every table has a non-NULL primary key.
Referential integrity
StudentSkill.student_user_id references StudentProfile; mentor skill references MentorProfile; booking 
references one allocation and one availability slot; session references booking.
Domain integrity
Ratings between 1 and 5; experience >= 0; end time > start time; controlled status values.
Uniqueness
Email, skill name, domain name, student number; one allocation per request; one session per booking.
Business integrity
Only pending request can be accepted/rejected/cancelled; only active allocation can be booked.
Temporal integrity
No overlapping confirmed bookings for a student; one active booking per mentor slot.
Historical integrity
Do not silently delete rejected/cancelled requests or completed sessions; retain audit history.
8.4 Referential action policy

Use ON DELETE RESTRICT for users and master data referenced by business history. Deactivate accounts, skills or 
domains instead of hard deleting them.

Use ON DELETE CASCADE only for purely dependent, disposable bridge rows if hard-delete policy is explicitly 
approved. It should not erase bookings, sessions, feedback or audit evidence.

Use ON UPDATE RESTRICT for surrogate identifiers. Identifiers should be immutable; descriptive values can be 
updated in their owning entity.
SOURCE-OF-TRUTH RULE
MySQL owns the official profile, request, allocation, availability, booking, session, rating and feedback values. Redis 
cache entries and Neo4j graph projections must be rebuildable from MySQL and must not override transactional 
decisions.

WHY BOOKING DOES NOT REPEAT PARTICIPANT OR TIME COLUMNS
The current Business Rules Catalogue includes an illustrative booking implementation that copies student_id, 
mentor_id, start_at and end_at into BOOKING. This specification instead stores allocation_id and availability_id only.

10. Triggers, stored procedures, transaction boundaries and 
outbox
The DBMS Unit 2 material defines triggers as automatic actions caused by INSERT, UPDATE or DELETE events and 
stored procedures as named server-side programs with IN / OUT / INOUT parameters. In AlumniConnect, use triggers 
for last-line row-level validation and optional audit capture; use procedures for actor-aware, multi-row workflows, 
capacity checks, locking, booking overlap checks and outbox insertion.
10.1 What belongs in a trigger vs a procedure
Use a trigger for
Use a stored procedure for
Validate a row-level state transition before the change.
Accept/reject a request and create its allocation atomically.
Capture OLD and NEW values for important changes when direct 
DML is permitted.
Book a slot after locking student, mentor, allocation and 
availability rows.
Reject invalid row-local status transitions or values.
Insert outbox events and coordinate all related records in the 
same transaction.
Enforce simple row-local rules that apply to all writers.
Check cross-row rules, capacity, overlap and coordinated multi-
table updates.
DO NOT SEND EMAIL FROM A TRIGGER
A trigger must not call external APIs, send email or depend on a network service. The business procedure writes one 
transactional outbox event before COMMIT; a worker delivers it only after commit and retries failures safely.
10.2 Trigger - validate request state transitions
Allowed transition from the blueprint: PENDING -> ACCEPTED, REJECTED or CANCELLED. Once a request has left 
PENDING, the status cannot be changed again through this trigger. If the team later needs reopen/resubmit, define a 
separate explicit transition and audit it.
DELIMITER $$
CREATE TRIGGER trg_request_status_guard
BEFORE UPDATE ON mentorship_request
FOR EACH ROW
BEGIN
  IF OLD.request_status <> NEW.request_status THEN
    IF OLD.request_status <> 'PENDING'
       OR NEW.request_status NOT IN ('ACCEPTED','REJECTED','CANCELLED') THEN
      SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Invalid mentorship request status transition';
    END IF;
  END IF;
END$$
DELIMITER ;

10.3 Trigger - audit request status changes (optional)
This optional AFTER trigger captures OLD and NEW state values for every request status update. A database trigger 
cannot automatically know the authenticated web user unless a trusted application context is propagated to the same 
connection. The example therefore writes a NULL actor for system/database-level evidence. In a deployment that 
requires human attribution, write the actor-specific audit row inside the stored procedure and disable this trigger to 
avoid duplicate audit rows.
DELIMITER $$
CREATE TRIGGER trg_request_status_audit
AFTER UPDATE ON mentorship_request
FOR EACH ROW
BEGIN
  IF OLD.request_status <> NEW.request_status THEN
    INSERT INTO audit_log
      (actor_user_id, entity_type, entity_id, action,
       old_values_json, new_values_json, occurred_at)
    VALUES
      (NULL, 'MENTORSHIP_REQUEST', NEW.request_id, 'STATUS_CHANGED',
       JSON_OBJECT('status', OLD.request_status),
       JSON_OBJECT('status', NEW.request_status), UTC_TIMESTAMP(6));
  END IF;
END$$
DELIMITER ;
Outbox insertion is deliberately handled by the business procedure rather than this trigger. The procedure knows the 
actor, event payload and recipient set, and can use a stable dedupe_key. Both the audit row and outbox row 
participate in the surrounding transaction and roll back with it.

10.4 Trigger - validate session lifecycle
DELIMITER $$
CREATE TRIGGER trg_session_status_guard
BEFORE UPDATE ON mentorship_session
FOR EACH ROW
BEGIN
  IF OLD.session_status <> NEW.session_status THEN
    IF OLD.session_status <> 'SCHEDULED'
       OR NEW.session_status NOT IN ('COMPLETED','CANCELLED','NO_SHOW') THEN
      SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Invalid session status transition';
    END IF;
  END IF;
 
  IF NEW.actual_start_at IS NOT NULL
     AND NEW.actual_end_at IS NOT NULL
     AND NEW.actual_end_at < NEW.actual_start_at THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Session end cannot precede session start';
  END IF;
 
  IF NEW.session_status = 'COMPLETED'
     AND (NEW.actual_start_at IS NULL OR NEW.actual_end_at IS NULL) THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Completed session requires actual start and end times';
  END IF;
END$$

10.5 Trigger - feedback eligibility
Session feedback is allowed only after the session has been completed and only for one of the actual participants. The 
database trigger is a last-line integrity guard; the stored procedure and FastAPI authorization layer must still validate 
the authenticated actor and keep duplicate submissions idempotent.
DELIMITER $$
CREATE TRIGGER trg_feedback_participant_guard
BEFORE INSERT ON session_feedback
FOR EACH ROW
BEGIN
  DECLARE v_student BIGINT UNSIGNED DEFAULT NULL;
  DECLARE v_mentor BIGINT UNSIGNED DEFAULT NULL;
  DECLARE v_status VARCHAR(20) DEFAULT NULL;
 
  SELECT mr.student_user_id, mr.mentor_user_id, ms.session_status
    INTO v_student, v_mentor, v_status
  FROM mentorship_session ms

10.6 Trigger - protect allocation and booking status transitions
These row-level guards prevent direct SQL updates from reopening ended allocations or confirming a cancelled 
booking. The application should route business changes through stored procedures, while triggers provide a final 
defense for writers that reach the tables directly.
DELIMITER $$
CREATE TRIGGER trg_allocation_status_guard
BEFORE UPDATE ON mentor_allocation
FOR EACH ROW
BEGIN
  IF OLD.allocation_status <> NEW.allocation_status THEN
    IF OLD.allocation_status <> 'ACTIVE' OR NEW.allocation_status <> 'ENDED' THEN
      SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Allocation can transition only from ACTIVE to ENDED';
    END IF;
  END IF;
END$$
 
CREATE TRIGGER trg_booking_status_guard
BEFORE UPDATE ON booking
FOR EACH ROW
BEGIN
  IF OLD.booking_status <> NEW.booking_status THEN
    IF OLD.booking_status <> 'CONFIRMED' OR NEW.booking_status <> 'CANCELLED' THEN
      SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Booking can transition only from CONFIRMED to CANCELLED';
    END IF;
  END IF;
  IF NEW.booking_status = 'CANCELLED' AND NEW.cancelled_at IS NULL THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Cancelled booking requires cancelled_at';
  END IF;
END$$

10.9 Stored procedure - create a confirmed booking atomically
The procedure validates the active allocation, confirms that the slot belongs to the allocation mentor, locks both 
participants and the availability row, checks overlap for both student and mentor, reserves the slot, creates the 
session and records the outbox event in one transaction. The generated unique active_availability_id is the final guard 
against double booking of one slot.
DELIMITER $$
CREATE PROCEDURE sp_create_confirmed_booking(
  IN p_allocation_id BIGINT UNSIGNED,
  IN p_availability_id BIGINT UNSIGNED,
  IN p_actor_user_id BIGINT UNSIGNED,
  IN p_idempotency_key VARCHAR(100),
  OUT p_booking_id BIGINT UNSIGNED
)
booking_proc: BEGIN

  DECLARE v_mentor BIGINT UNSIGNED;
  DECLARE v_allocation_status VARCHAR(20);
  DECLARE v_slot_mentor BIGINT UNSIGNED;
  DECLARE v_start DATETIME(6);
  DECLARE v_end DATETIME(6);
  DECLARE v_slot_status VARCHAR(20);
  DECLARE v_overlap INT DEFAULT 0;
  DECLARE v_student_status VARCHAR(20);
  DECLARE v_mentor_status VARCHAR(20);
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;
    RESIGNAL;
  END;
 
  SET p_booking_id = NULL;
 
  -- Discover the lock targets before opening the transaction. This avoids
  -- establishing a REPEATABLE READ snapshot before participant locks are acquired.
  SELECT mr.student_user_id, mr.mentor_user_id
    INTO v_student, v_mentor
  FROM mentor_allocation ma
  JOIN mentorship_request mr ON mr.request_id = ma.request_id
  WHERE ma.allocation_id = p_allocation_id;
  IF v_student IS NULL OR v_mentor IS NULL THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Allocation does not exist';
  END IF;
 
  IF p_idempotency_key IS NULL THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'An idempotency key is required';
  END IF;
 
  -- Idempotency lookup is outside the transaction so it cannot establish a stale
  -- REPEATABLE READ snapshot before the participant locks. It returns a replay only
  -- for the same actor, allocation and slot. A conflicting reuse is rejected by UNIQUE.
  SELECT MAX(b.booking_id) INTO p_booking_id
  FROM booking b
  JOIN mentor_allocation ma2 ON ma2.allocation_id = b.allocation_id
  JOIN mentorship_request mr2 ON mr2.request_id = ma2.request_id

    AND b.availability_id = p_availability_id;
  IF p_booking_id IS NOT NULL THEN
    LEAVE booking_proc;
  END IF;
 
  IF v_student <> p_actor_user_id THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Only the allocation student may create the booking';
  END IF;
 
  START TRANSACTION;
 
  -- Global lock order serializes overlap checks for both participants.
  SELECT ua.account_status INTO v_student_status
  FROM student_profile sp
  JOIN user_account ua ON ua.user_id = sp.user_id
  WHERE sp.user_id = v_student
  FOR UPDATE;
 
  SELECT ua.account_status INTO v_mentor_status
  FROM mentor_profile mp
  JOIN user_account ua ON ua.user_id = mp.user_id
  WHERE mp.user_id = v_mentor

  SELECT ma.allocation_status, mr.student_user_id, mr.mentor_user_id

10.13 Transaction, ACID, isolation, locking and cross-store consistency
ACID property
AlumniConnect application
Atomicity
Accept-request transaction commits allocation + request status + audit + outbox together. Booking transaction 
commits booking + availability state + scheduled session + outbox together.
Consistency
PK/FK/UNIQUE/CHECK constraints, state guards and procedures preserve legal request, allocation, booking, session 
and review states.
Isolation
Concurrent acceptance and booking operations lock shared parent profile rows before checking capacity or 
overlapping appointments. The chosen lock order must be consistent.
Durability
After COMMIT, InnoDB redo/undo and recovery protect committed rows according to the database durability 
configuration.
Lock order and concurrency pattern
Use a predictable lock order for every path that touches the same business objects: StudentProfile -> MentorProfile -> 
Request/Allocation -> Availability -> Booking/Session. A transaction that ends an allocation or cancels a booking must 
follow a compatible order. Inconsistent lock order increases deadlock risk.

Mentor capacity: serialize acceptance operations by locking the MentorProfile row before reading active allocation 
count and inserting a new allocation. The initial request read is only to discover lock targets; re-read the request 
under FOR UPDATE after participant locks.

Student/mentor overlap: serialize bookings by locking both participant profile rows, then the allocation and 
availability slot, then check for overlapping CONFIRMED bookings.

Use half-open time intervals [start, end). Two intervals overlap when existing_start < requested_end AND 
existing_end > requested_start. Adjacent intervals (10:00-10:30 and 10:30-11:00) do not overlap.

A UNIQUE generated active_availability_id prevents two CONFIRMED bookings against the same slot even when 
concurrent code paths race. A profile lock is still required for overlap checks across different slots.

Retry deadlock victims and lock-wait timeouts at the application boundary using the same idempotency key. Retry 
only transactions designed to be safe to execute again.
Isolation-level guidance
Isolation level
Use / implication
READ UNCOMMITTED
Not recommended for booking or allocation decisions; dirty reads are unacceptable.
READ COMMITTED
A practical option for workflow transactions because each ordinary read obtains a fresh committed snapshot. 
Parent-row locks still serialize the relevant participants.
REPEATABLE READ
MySQL InnoDB default. Be careful: a plain consistent read can use a snapshot created before a lock wait. Discover 
lock targets before START TRANSACTION, then lock and re-read authoritative rows; use current/locking reads for 
critical predicates or set READ COMMITTED for the workflow transaction.

Transactional outbox and polyglot persistence
The SQL transaction writes NotificationOutbox beside the business update. After COMMIT, a worker claims events 
with a short locking transaction (MySQL 8 can use FOR UPDATE SKIP LOCKED for queue workers), marks them 
PROCESSING, delivers notifications or projects updates, and marks SENT. Failures increment attempt_count and set 
next_attempt_at / last_error. Dedupe keys make repeated worker runs idempotent.

Redis invalidation and Neo4j projection happen after MySQL commit. They are eventually consistent and 
rebuildable; they are never used to approve an allocation or confirm a slot.

Do not perform HTTP calls, send email or update Neo4j from a MySQL trigger. Triggers run inside the SQL 
transaction and external side effects cannot be rolled back.

Availability.slot_status = BOOKED is a transaction-maintained operational state that mirrors the active booking 
relation. The booking procedure and cancellation procedure must update both in one transaction; include a 
reconciliation query in operations tests.
Example reconciliation queries
-- Slot marked BOOKED without a confirmed booking (should return no rows)
SELECT a.availability_id
FROM mentor_availability a
LEFT JOIN booking b
  ON b.availability_id = a.availability_id
 AND b.booking_status = 'CONFIRMED'
WHERE a.slot_status = 'BOOKED'
  AND b.booking_id IS NULL;
 
-- Confirmed booking whose slot is not marked BOOKED (should return no rows)
SELECT b.booking_id, a.availability_id, a.slot_status
FROM booking b
JOIN mentor_availability a ON a.availability_id = b.availability_id
WHERE b.booking_status = 'CONFIRMED'
  AND a.slot_status <> 'BOOKED';
TRANSACTION RULE
Never split a booking reservation into “check availability” in one transaction followed by “insert booking” in another. 
The check, slot update, booking row, session row and outbox event form one atomic transaction.

11.2 Views for safe, reusable reporting
A view provides a reusable logical projection. It is useful for hiding private columns and for exposing normalized 
relationships without copying them into base tables.

Create a public mentor directory view that exposes display_name, job_title, company, skills, domains and public 
summary, but omits email, password hash and private contact data.

Create a student mentorship-history view joining requests, allocations, bookings and sessions. Do not materialize a 
second copy of status data unless a measured reporting requirement justifies it.

Create mentor-rating aggregates from completed-session reviews. Calculate average rating from MentorReview 
rows rather than storing a writable duplicate average in MentorProfile.
CREATE VIEW vw_booking_details AS
SELECT b.booking_id, b.booking_status,
       mr.student_user_id, mr.mentor_user_id,
       a.starts_at, a.ends_at,
       ma.allocation_status
FROM booking b
JOIN mentor_allocation ma ON ma.allocation_id = b.allocation_id
JOIN mentorship_request mr ON mr.request_id = ma.request_id
JOIN mentor_availability a ON a.availability_id = b.availability_id;

11.3 User-defined functions - when they are useful
A MySQL function returns one value and is appropriate for deterministic calculations reused in SELECT expressions. 
Do not use a function to create bookings, send notifications or perform multi-row workflow changes; those belong in 
stored procedures.
DELIMITER $$
CREATE FUNCTION fn_rating_band(p_rating DECIMAL(3,2))
RETURNS VARCHAR(12)
DETERMINISTIC
BEGIN
  RETURN CASE
    WHEN p_rating IS NULL THEN 'UNRATED'
    WHEN p_rating >= 4.50 THEN 'EXCELLENT'
    WHEN p_rating >= 3.50 THEN 'GOOD'
    WHEN p_rating >= 2.50 THEN 'AVERAGE'
    ELSE 'LOW'
  END;
END$$
DELIMITER ;
 
-- Example use with a completed-review aggregate query:
SELECT mr2.mentor_user_id,
       AVG(r.rating) AS average_rating,
       fn_rating_band(AVG(r.rating)) AS rating_band
FROM mentor_review r
JOIN mentorship_session ms ON ms.session_id = r.session_id
JOIN booking b ON b.booking_id = ms.booking_id
JOIN mentor_allocation ma ON ma.allocation_id = b.allocation_id
JOIN mentorship_request mr2 ON mr2.request_id = ma.request_id
WHERE ms.session_status = 'COMPLETED'
GROUP BY mr2.mentor_user_id;

Appendix A. Glossary and design references
Term
Meaning in this specification
1NF
All relation attributes have atomic values; no repeating groups or nested sets.
2NF
1NF plus every non-prime attribute fully depends on every candidate key.
3NF
For every non-trivial FD X -> A, X is a superkey or A is prime.
BCNF
For every non-trivial FD X -> A, X is a superkey.
Candidate key
Minimal superkey. One candidate key is selected as the primary key.
Functional dependency
A constraint stating that an attribute set determines another attribute set.
Attribute closure
Set of attributes functionally implied by a starting attribute set.
Lossless join
Decomposition can be rejoined without losing information or creating spurious tuples.
Dependency preservation
Dependencies can be enforced in individual decomposed relations without joins.
Associative relation
A relation representing an M:N relationship; it often has a composite primary key.
Transactional outbox
An event row written in the same database transaction as the business change; external delivery occurs 
asynchronously after commit.
Idempotency key
Client/request token used to prevent retries from creating duplicate business operations.
