1. Executive Summary and Design Basis
AlumniConnect is a mentorship, career-guidance and mock-interview platform. Students discover relevant 
alumni, submit mentorship requests, schedule sessions, attend offline meetings, receive feedback and track 
progress. Alumni manage their professional profiles and availability, respond to requests, and record session 
outcomes. Administrators manage users, departments, skills, mentorship domains and platform analytics.
The central design recommendation is a modular monolith with polyglot persistence: one backend application 
with clearly separated business modules, MySQL as the authoritative relational database, Redis as a performance 
layer and Neo4j as a recommendation graph. This avoids splitting tightly related booking and allocation 
workflows across independently deployed services.
Figure 1. Each technology has a bounded responsibility; SQL remains authoritative for business decisions.
1.1 What this catalogue is intended to protect

Correct lifecycle transitions: pending requests cannot be accepted twice; cancelled requests cannot later 
create allocations.

Referential consistency: an allocation must correspond to the request that created it; a session must 
correspond to a valid booking.

Scheduling correctness: one slot cannot be actively booked twice, and neither participant can have 
overlapping confirmed appointments.

Trustworthy feedback: only actual participants can submit feedback, and mentor reviews require a completed 
session.

Reliable side effects: notifications are queued within the same SQL transaction as the business change and 
delivered after commit.

Concurrency safety: concurrent requests and bookings must not bypass validation due to timing or race 
conditions.
1.2 Normative terms
MUST means a non-negotiable integrity or security requirement. SHOULD means the recommended default, with 
deviations documented. MAY means an optional enhancement. A rule labelled [R] is a proposed decision and 
should be confirmed by the team before implementation.

Request is not allocation
A recommendation is only a candidate. A student request is a formal invitation. An allocation exists only after the 
mentor accepts the pending request and the database commits the request status update and allocation insert 
together.
Booking is not session

4.3 Required acceptance behaviour
1.
Lock the relevant student and mentor records in a consistent order, then lock and re-read the request row.
2.
Verify that the request is still PENDING and the authenticated actor is the target mentor.
3.
Check that mentor capacity and any student-side allocation policy are satisfied.
4.
Insert the allocation with the request ID protected by a unique constraint.
5.
Update the request to ACCEPTED and set decision metadata.
6.
Insert the student notification into the outbox before COMMIT. A worker sends it only after commit.

6. Availability and Booking Rules
Scheduling is the highest-risk consistency area because multiple students may attempt to reserve the same mentor 
slot and a student may attempt to book two different mentors for overlapping times. The blueprint explicitly 
requires the system to check slot availability, student overlap, mentor capacity, valid allocation/request and 
duplicate submission before confirming a booking.

6.3 Time-overlap definition
Use half-open intervals
Treat appointments as [start_at, end_at). Two intervals overlap exactly when existing.start_at < requested.end_at AND 
existing.end_at > requested.start_at. This allows a 10:00-10:30 session to be followed by a 10:30-11:00 session without 
a false conflict.
Overlap predicate used inside the booking transaction
SELECT COUNT(*) INTO v_conflicts
FROM booking b
WHERE b.status = 'CONFIRMED'
  AND b.start_at < v_requested_end
  AND b.end_at   > v_requested_start
  AND (b.student_id = v_student_id
       OR b.mentor_id = v_mentor_id);
 
IF v_conflicts > 0 THEN
  SIGNAL SQLSTATE '45000'
    SET MESSAGE_TEXT = 'Student or mentor has an overlapping booking';
END IF;

Why generated active_slot_id?
A simple UNIQUE(slot_id) would also block rebooking a slot after the previous booking was cancelled if cancelled

9.3 What constraints cannot safely do alone

A CHECK constraint cannot reliably compare a booking against all other bookings to detect overlapping time 
intervals.

A CHECK constraint cannot verify that the selected mentor is the same mentor who owns the allocation and 
the availability slot.

A UNIQUE key can enforce one active slot reservation through a generated key, but it does not by itself 
prevent a student booking two different overlapping slots.

Capacity counts, state transitions and notifications span several rows; they require a transaction and 
consistent locking policy.

A trigger is not a substitute for a complete business transaction or an authorization layer.

10.4 Trigger implementation cautions

MySQL triggers execute once per affected row. A bulk UPDATE can therefore produce many audit rows.

Trigger writes participate in the same transaction as the triggering statement. If the transaction rolls back, 
trigger writes roll back too.

Keep triggers short and deterministic. Do not call external services or attempt email delivery.

Do not place COMMIT, ROLLBACK or START TRANSACTION inside a trigger.

Avoid hidden multi-table workflows and recursive trigger patterns. Put business orchestration in a procedure.

Do not rely on CURRENT_USER() to identify the application’s human actor; it identifies the database principal.

Restrict direct DML on sensitive tables so application code cannot bypass procedures and authorization 
checks.

  IF v_count = 0 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Session not found';
  END IF;
 
  START TRANSACTION;
 
  SELECT b.student_id, sp.user_id, ms.status
    INTO v_student_id, v_student_user_id, v_session_status
  FROM mentorship_session ms
  JOIN booking b ON b.booking_id = ms.booking_id
  JOIN student_profile sp ON sp.student_id = b.student_id
  WHERE ms.session_id = p_session_id
  FOR UPDATE;
 
  IF v_student_user_id <> p_actor_user_id THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Only the session student may review the mentor';
  END IF;
 
  IF v_session_status <> 'COMPLETED' THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'A mentor review requires a completed session';
  END IF;
 
  INSERT INTO mentor_review
    (session_id, student_id, rating, review_text, created_at)
  VALUES
    (p_session_id, v_student_id, p_rating,
     p_review_text, CURRENT_TIMESTAMP(6));
 
  INSERT INTO business_event_log
    (actor_user_id, entity_type, entity_id, action_type,
     payload, occurred_at)
  VALUES
    (p_actor_user_id, 'MENTOR_REVIEW', p_session_id, 'REVIEW_SUBMITTED',
     JSON_OBJECT('rating', p_rating), CURRENT_TIMESTAMP(6));
 
  COMMIT;
END$$
DELIMITER ;
Keep UNIQUE(session_id, student_id) on mentor_review even when the procedure checks for eligibility. The 
database uniqueness rule is the final protection against two concurrent duplicate submissions.

12.3 Locking strategy

Use InnoDB row-level locks for the records that represent the resources being changed.

Use SELECT ... FOR UPDATE on the mentor availability row to serialize attempts to claim the same slot.

Also lock the student profile and mentor profile rows before overlap checks. These parent rows act as 
serialization points for all booking operations involving either participant.

Adopt one fixed lock order for every related procedure, for example: student profile -> mentor profile -> 
allocation -> availability slot -> booking/session.

Re-read status after acquiring locks. A value read before the lock is only a discovery hint, not proof that it is 
still valid.

Keep the transaction short. Do not call email providers, Redis, Neo4j or remote APIs while holding database 
locks.
12.4 Isolation level guidance
InnoDB commonly uses REPEATABLE READ as its default isolation level, but confirm the actual server setting. For 
this application, use explicit locking reads for booking/acceptance decisions and never rely on a plain SELECT

12.5 Deadlocks and retry behaviour
Two-phase locking can ensure conflict-serializable behaviour but does not eliminate deadlocks. The Unit 4 slides 
demonstrate a deadlock when two transactions obtain locks in different orders and MySQL rolls one transaction 
back. AlumniConnect should therefore use a consistent lock order, short transactions, suitable indexes and 
bounded retry for transient deadlock errors.
MySQL condition

1213 - Deadlock found
Retry the entire transaction/procedure with a small bounded 
retry count and jitter. Do not retry only the final statement.
1205 - Lock wait timeout
Roll back the full business operation, return a retryable error 
where appropriate, and log contention.
1062 - Duplicate key
Interpret by constraint name: slot already reserved, request 
already allocated, review already submitted, or idempotency 
replay. Return a meaningful result.
45000 - Business rule SIGNAL
Do not blindly retry. Return a domain validation error to the UI.
12.6 Transactional outbox pattern
7.
Within the same SQL transaction as the state change, insert an outbox row with event type, aggregate ID, 
recipient and payload.
8.
Commit the business record and outbox row together.
9.
A worker polls pending outbox rows after commit, sends the notification, and marks delivery status.
10. Use event IDs and recipient-level unique keys so worker retries do not duplicate deliveries.
11. If delivery repeatedly fails, retain the event for retry/dead-letter inspection; never undo the accepted request 
or confirmed booking.

13.2 Stored functions
Use a stored function for a reusable scalar calculation, not for a multi-step workflow. Candidate examples are 
profile completeness, a normalised rating metric or a small derived label. Functions should not be used to send 
notifications or modify booking state.
Illustrative read-only function for mentor rating summary
DELIMITER $$
CREATE FUNCTION fn_mentor_average_rating(p_mentor_id BIGINT)
RETURNS DECIMAL(3,2)
READS SQL DATA
BEGIN
  DECLARE v_avg DECIMAL(3,2);
 
  SELECT ROUND(AVG(mr.rating), 2)
    INTO v_avg
  FROM mentor_review mr
  JOIN mentorship_session ms ON ms.session_id = mr.session_id
  JOIN booking b ON b.booking_id = ms.booking_id
  WHERE b.mentor_id = p_mentor_id
    AND ms.status = 'COMPLETED';
 
  RETURN COALESCE(v_avg, 0.00);
END$$

13.4 Indexing guidelines

Index foreign keys and frequently filtered status/time columns: (mentor_id, status, start_at), (student_id, 
status, start_at), and (allocation_id, status).

Use composite indexes in the order that matches actual predicates and sort order; verify with EXPLAIN rather 
than indexing every column.

Make the overlap predicate sargable where possible and inspect actual plans on realistic data volumes.

Keep unique constraints even when application checks exist; they protect correctness under concurrency.

Measure write overhead and storage cost before adding redundant indexes.


MySQL wins if data differs between stores.

Redis entries are rebuildable and expire through TTL. Invalidate caches after the authoritative SQL commit.

Neo4j is a projection of selected MySQL entities. Changes should be propagated asynchronously and may be

15.2 Privacy and retention

Use least privilege: students see public mentor profile attributes and their own private records; mentors see 
relevant student information for their accepted allocations and sessions.

Do not expose private email, phone, internal notes or admin-only audit fields in the public mentor directory.

Use soft deactivation for accounts and retain required business history. Define a documented 
retention/deletion policy for personal data separately.

Review text and session notes should be access-controlled and should not contain passwords, tokens, financial 
account information or unrelated sensitive information.

Audit access to administrative views and sensitive exports where practical.
15.3 Data deletion policy
Do not cascade-delete requests, allocations, bookings, sessions, feedback or reviews when an account is 
deactivated. Prefer status changes and restricted deletion. If legal/privacy deletion is later required, define a 
controlled anonymisation procedure that preserves referential integrity and legitimate aggregate reporting while 
removing or minimising personal identifiers.

Final implementation principle
A UI check improves user experience, but it is not an integrity guarantee. The durable guarantee belongs in MySQL:
