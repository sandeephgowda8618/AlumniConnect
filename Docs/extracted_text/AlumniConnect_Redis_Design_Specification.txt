01 / Executive summary and design boundary
AlumniConnect uses a modular monolith with polyglot persistence. FastAPI is the single logical API boundary. MySQL 8.x with
InnoDB owns durable business records and transactional decisions. Redis is a performance layer for cacheable reads and
short-lived state. Neo4j provides relationship-based mentor discovery. This Redis specification defines only the Redis
responsibility; it does not move business ownership out of MySQL.

1.2 Non-negotiable boundaries
•  MySQL wins on disagreement. Redis entries are rebuildable and must not override authoritative rows.
•  Authorization always executes. A cache hit is not permission to view a record.
•  Booking always revalidates in MySQL. The booking transaction locks and validates the current availability row, allocation
and overlap rules.
•  Outbox drives secondary changes. A business update and its outbox event commit together; a worker invalidates Redis
after commit.
IMPORTANT
A cached availability preview is a user-interface convenience only. It may become stale immediately after another user books the slot. The
booking procedure must re-read and lock MySQL rows regardless of Redis contents.

03 / Key naming convention
Use one predictable namespace for all keys. This prevents collisions between environments and makes keys searchable
during development. Key names should communicate product, deployment environment, schema version, feature area and
entity identity. Avoid names that include email addresses, phone numbers, names or other personal data.
RECOMMENDED KEY GRAMMAR
ac:{environment}:v{schema}:{feature}:{resource}:{identifier}:{variant}
Example: ac:prod:v1:mentor:profile:482:public
3.1 Naming components
COMPONENT
RULE
EXAMPLE
Product prefix
Constant prefix for every AlumniConnect key.
ac
Environment
Use dev, test, staging or prod. Never share cache namespaces across
environments.
prod
Schema version
Increment when the key meaning or payload shape changes incompatibly.
v1
Feature area
Use a stable bounded vocabulary.
mentor, catalog, rec, auth, rate, idem, ranking, feed
Resource
Describe the cached object or state.
profile, skills, domains, result, challenge, counter
Identifier
Use immutable MySQL IDs, not mutable names.
482, 901, user_id
Variant / dimensions
Add public/private, date, domain, filter digest or other query dimensions as
needed.
public, 2026-11-02, f:9e31
3.2 Rules for stable and safe keys
•  Use lowercase ASCII and colon separators. Avoid spaces and arbitrary user-supplied strings.
•  Use numeric or opaque stable IDs. A mentor changing their display name must not change their key identity.
•  Include all result-shaping filters in recommendation keys. Canonicalise the filter object and hash it (for example, SHA-256
truncated to 12-16 hex characters).
•  Include an explicit payload/schema version. Do not silently reuse a key after changing the cached JSON contract.
•  Do not encode access tokens, emails, phone numbers, request objectives or free-text biography content in key names.
•  Keep environment separation in the key even when different Redis instances are used; it protects local development and test
tooling.

5.1 Optional version keys
Version keys are invalidation metadata, not cached business data. Initialise a missing version to 1 or 0 and increment it after
the committed business change has been observed. Do not apply a short TTL to version counters: accidental expiry could
make an old versioned cache key appear current again. If the Redis instance is rebuilt, increment a deployment-wide cache
epoch or change the schema namespace (for example, v2).
5.2 Optional availability preview
STRICT PREVIEW RULE
An availability preview may be cached for a very short display interval. The booking service must ignore that cached value, read and lock the
relevant MySQL availability row, validate overlapping appointments and capacity, then commit the booking and outbox event atomically.
5.3 Data minimisation
Prefer a small display projection over serialising entire ORM entities. Cache only what the receiving screen needs. Do not
cache user credentials, plaintext OTP values, private contact fields for public access, or complete review/session text. Apply
backend authorization even when the data came from a cache.

6.1 Selection rules
•  HASH: use for a compact mentor profile card or a catalogue mapping. Keep fields small and stable.
•  STRING: use for a JSON blob when the application reads the whole recommendation response as one unit; include a
schema version.
•  SET: use when uniqueness and membership matter, not when order matters.
•  SORTED SET: use for precomputed ranking. A ranking score is not a booking permission or live eligibility fact.
•  LIST: use for a lightweight feed. Trim it on each append and never use it as permanent event history.
•  STREAM: use only if the team needs event-like consumption or consumer-group features; it is optional for the core release.
6.2 Avoid premature structure complexity
Do not create a Redis key for every MySQL table. Choose a structure because it supports a real read or temporary-state
pattern. For the first implementation, the minimum useful set is: HASH for mentor profiles and reference catalogues; STRING
for recommendation JSON, counters, challenges and idempotency; SORTED SET for rankings; LIST for recent activity. Add
STREAM only when there is a clear requirement.

7.1 TTL implementation practices
•  Set the expiry at the time the value is written: SET key value EX 600 or write fields then EXPIRE key 600.
•  Check TTL during debugging with TTL key. Redis reports -2 when the key is absent and -1 when it exists without expiry.
•  Add small random jitter to high-volume cache TTLs (for example, 600 seconds plus or minus 60 seconds) to avoid many
keys expiring simultaneously.
•  Do not rely on expiry alone for user-visible freshness. Events must invalidate profile/recommendation/catalogue caches after
SQL commit.
•  For lists or streams, limit both time and size. TTL alone does not prevent a single key from growing without bound before
expiry.
POLICY STATUS
All concrete TTLs in this section are proposed defaults, not explicit requirements from the uploaded blueprint or PRD. Record final values in
application configuration so they can be tuned without code changes.

08 / Cache-aside read path
Cache-aside is the default read pattern for mentor cards, reference catalogues and recent recommendations. The application,
not Redis, decides how to rebuild a missing value.
1. API request
2. Redis GET
3. MySQL read
4. Redis SET + TTL
HIT: return cached display payload
MISS: query MySQL / discovery path
Authorization still runs; cache never confirms a booking.

STEP
ACTION
RESULT
1. Authorize
Authenticate the actor and check role/resource permissions before exposing a cached
payload.
Unauthorized request is rejected even when Redis
contains the key.
2. Build key
Build the environment/version/resource key including IDs, variant and relevant filter
digest.
Deterministic cache key.
3. GET
Read Redis. If found, validate payload/schema version and return permitted display

4. MISS

8.2 Cache stampede protection
When many requests miss the same hot key, they can all query MySQL. For expensive mentor-card or recommendation
rebuilds, use a short-lived lock key with SET lock-key token NX EX 10. The lock owner rebuilds the cache; other
requests briefly wait, serve a safe stale display copy if one exists, or perform a bounded fallback. Always release a lock only if
the stored token matches the owner token (a Lua compare-and-delete script); never blindly DEL another worker’s lock.
8.3 Cache payload validation
•  Include schema_version and a generated timestamp in JSON response caches.
•  Reject malformed or unsupported cached data; delete it and rebuild from the authoritative source.
•  Do not cache a response that includes fields the current actor is not allowed to view.
•  On a cold cache or Redis outage, fall back to the normal MySQL/discovery path where safe; apply timeouts so Redis does
not stall the request.

09 / Cache invalidation design
TTL limits how long a value can survive, but it is not a complete freshness strategy. AlumniConnect should invalidate relevant
cache entries after the authoritative MySQL transaction commits. The supplied requirements explicitly call for profile-change
invalidation and outbox-driven cache invalidation.
9.1 Invalidation mechanisms
MECHANISM
HOW IT WORKS
WHEN TO USE
Targeted DEL
Delete a known profile, catalogue or availability-preview key.
A single entity key has a known deterministic name.
Version / epoch bump
Increment a version key used in derived cache keys; new reads naturally
use a new namespace. Old values expire by TTL.
Recommendation results or caches that depend on
many entities.
Reverse index set (advanced)
Maintain a SET of cache keys associated with a mentor/student/domain
and delete those members on change.
Only if the project later needs highly targeted invalidation
at larger scale; keep index cleanup bounded.
TTL expiry
Allow an entry to disappear after a maximum age.
Safety net for every ordinary cache; not a substitute for
event invalidation.
9.2 Recommended first-release strategy
Mentor profile: targeted delete of the mentor public-card HASH, then increment the mentor version. Recommendation
results: increment one global recommendation epoch after any relevant mentor/student skill/domain, mentor visibility/status,
capacity/allocation, or rating change. Recommendation keys include the epoch. This is intentionally simple and safe for a small
academic dataset; it invalidates more results than strictly necessary, but old results expire naturally.
INCR ac:prod:v1:version:mentor:482
DEL ac:prod:v1:mentor:profile:482:public
INCR ac:prod:v1:version:recommendations
For a catalogue change, delete or version-bump the appropriate catalogue key and increment the recommendation epoch. For
an availability edit or booking/cancellation, delete any display-preview key for the affected mentor/date; the confirmed booking
remains in MySQL.
9.3 Never use production-wide wildcard deletion per entity
Avoid KEYS ac:prod:* in application code. It can block Redis while scanning a large keyspace. Use deterministic keys,
version namespaces and direct deletion. Use SCAN only for controlled maintenance or debugging, not as the normal
invalidation mechanism.

11 / Transactional outbox integration
Cache invalidation must not occur before the MySQL commit. Otherwise, a transaction that later rolls back could cause a
cache miss and rebuild from unchanged rows, or the inverse: a cache might be repopulated with data that was not committed.
The application architecture therefore records the invalidation event in the same transaction as the business update.

+ outbox event
Outbox worker

(version bump)

11.1 Required sequence
STAGE

11.2 Worker reliability requirements
•  Process only committed outbox rows.
•  Use event IDs and idempotent Redis commands: DEL of a missing key is safe; repeated INCR is not idempotent unless
deduplicated.
•  A repeated invalidation may cause an extra cache miss but cannot duplicate a business write. If strict event deduplication is
needed, use one Lua script (or equivalent atomic Redis operation) that checks the event marker, applies DEL/version changes
and records the marker as one atomic unit. Do not write a marker in a separate command before invalidating: a worker crash
between those steps could suppress a required retry.
•  Track pending, processed and failed status, attempts, last error and next retry time in MySQL.
•  Retry transient errors with bounded backoff. Do not silently discard failures.
•  If Redis is unavailable, do not roll back a committed profile update. Leave the outbox event pending and retry.
IMPORTANT RETRY DETAIL
DEL can safely be replayed. INCR can over-invalidate if the same outbox event is processed twice. Use event-level deduplication or
deterministic version values so a retry does not repeatedly advance the cache epoch.

12 / Temporary state: challenges, rate limits and
idempotency
These keys are operational helpers. They are not durable business records. Keep them narrowly scoped, short-lived and
protected from exposure in logs.
12.1 Login challenge
SET ac:prod:v1:auth:challenge:ch_7f2a <hashed-or-opaque-state> NX EX 300
GET ac:prod:v1:auth:challenge:ch_7f2a
DEL ac:prod:v1:auth:challenge:ch_7f2a
Recommended behaviour: generate a high-entropy challenge ID; store a hash/opaque verifier rather than the raw password or reusable
credential; expire in five minutes; limit verification attempts; consume it once after successful validation. Exact login method and retry policy are
open application-security decisions.
12.2 Fixed-window rate limiting
Example key: ac:prod:v1:rate:user:109:mentor-search:20261102T1200. Increment the counter and set the expiry
atomically on the first increment. A simple two-command INCR followed by EXPIRE can race if the process fails between
commands; use a Lua script or a transaction/pipeline pattern that guarantees first-write expiry.
-- Lua: increment and apply expiry once, atomically
local n = redis.call('INCR', KEYS[1])
if n == 1 then
redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return n
-- Example: fixed 60-second bucket; enforce threshold in FastAPI
Choose limits by operation risk: mentor search may have a higher limit than login verification or request submission. The numeric limits are policy
decisions and are intentionally not hard-coded in this document. Rate limiting should not be treated as a replacement for authentication,
authorization or abuse monitoring.
12.3 Request idempotency
SET ac:prod:v1:idem:109:booking:create:idem_abc \
"<request-hash>|IN_PROGRESS" NX EX 86400
When the request completes, store a compact outcome or stable result reference and status COMPLETED. If a retry arrives
with the same key and same request fingerprint, return the stored result. If the same key is reused for a different request body,
reject it. The booking itself remains protected by MySQL row locks, unique constraints and a transaction; Redis idempotency
alone is not enough.
12.4 Failure policy
KEY CATEGORY
IF REDIS IS UNAVAILABLE / KEY IS EVICTED
Profile/catalogue cache
Fall back to MySQL; slower but correct.
Recommendation cache
Recompute via Neo4j + MySQL validation, or return a controlled retry if dependencies are unavailable.
Login challenge
Fail the verification attempt safely and allow a new challenge; do not bypass verification.
Rate limit
Use application/API fallback or return controlled retry; never treat a missing counter as identity proof.
Idempotency
Rely on MySQL unique/idempotency constraints for durable writes; do not allow duplicate booking effects.

15 / Operations, memory and failure handling
Redis is a fast in-memory system, but memory is finite. Cache values should be bounded, observable and disposable. The
project should choose its max-memory policy based on which data is stored.
15.1 Eviction policy considerations
POLICY CONSIDERATION
ALUMNICONNECT GUIDANCE
General cache eviction
For a cache-dominant instance, a least-recently-used or least-frequently-used all-key eviction policy can be considered after
verifying every key can safely be recreated.
Version counters
Do not allow unplanned eviction/expiry to reset cache generations while old keys could still be read. Use a persistent version
key or change the deployment cache epoch after rebuild.
Auth/rate/idempotency keys
Eviction can invalidate challenges early, reset rate counters or remove idempotency results. Treat these as short-lived
helpers, not the only security or business guard. MySQL must protect durable writes.
Memory pressure
Monitor used memory, evictions, rejected writes, key cardinality and large payloads. Keep feed/list values bounded.
Persistence
Because cache values are rebuildable, persistence is not required for their correctness. Temporary security state and retry
safety must have an explicit failure policy if Redis restarts.
15.2 Recommended operational controls
•  Set connection and command timeouts in FastAPI; Redis latency must not block requests indefinitely.
•  Use a connection pool and a separate Redis client configuration for production and tests.
•  Apply authentication, network isolation and TLS where the deployment supports it; never expose Redis publicly.
•  Use a dedicated Redis ACL user with only required key prefixes and commands when supported by the deployment.
•  Separate cache keys from temporary auth/operational keys by prefix. For production scale, consider separate Redis
instances/policies if eviction behaviour must differ.
•  Do not log verification secrets, idempotency response bodies or full cached personal data.
15.3 Graceful degradation
If Redis is unavailable, the application should still behave correctly for ordinary reads by falling back to MySQL or the normal
discovery pipeline. It may be slower. For temporary security operations, fail safely rather than skipping verification. For
idempotent writes, rely on the relational constraints and transaction design so a Redis restart cannot create duplicate bookings
or allocations.

16 / Privacy and security rules for cached data
CONTROL
IMPLEMENTATION RULE
Public profile projection
Cache only the fields intentionally exposed in the mentor directory. Build this from a least-privilege SQL view/repository
projection.
Role-aware authorization
Authenticate and authorize every request before serving a cache hit. Cache keys are not access-control tokens.
Private records
Do not put private contact details, internal notes, administrative fields or complete session notes in public caches.
Temporary challenges
Use random opaque IDs and hashed/opaque challenge values; expire them; enforce one-time consumption and attempt limits.
Idempotency data
Store a request fingerprint and compact response reference where possible. Do not include sensitive request bodies in key
names.
Key isolation
Prefix by environment and application version; use separate credentials/ACLs for deployment environments.
Data lifecycle
Keep TTLs short for temporary state and bounded for feeds. Delete relevant cache keys after deactivation/visibility changes;
historical business records remain in MySQL.
Auditability
Redis is not the audit log. Authoritative administrative and business history remains in MySQL.
16.1 Public profile example
Safe fields (illustrative): mentor ID, display name, headline, professional title, company display name, years of experience,
public skills, public domain expertise, profile completeness flag.
Do not include: login email, phone number, raw account status details, admin moderation notes, private internal biography,
access tokens, password hashes or participant-only session notes. Exact visibility is controlled by the approved product
privacy model.
SECURITY RULE
A cached object is still data. Its presence in Redis does not make it public, and a cached result cannot bypass the role/ownership checks defined
by the API and business rules.

Appendix B / Definitions
TERM
MEANING IN THIS DESIGN
Cache-aside
The application checks Redis first; on a miss it reads from the source and caches a rebuildable result.
TTL
Time to live; the expiry duration associated with a Redis key.
Cache invalidation
Deleting or versioning a cached value after the source data changes.
Cache epoch
A version number embedded in derived keys so a new generation is used after a change.
Outbox
A durable MySQL event record inserted in the same transaction as the business change.
Idempotency key
A client-supplied unique request token used to make retries safe.
Cache stampede
A burst of simultaneous misses that causes many requests to rebuild the same value.
