1. Executive Summary and Design Position
AlumniConnect should recommend alumni mentors by combining graph-based relationship discovery with transparent, 
configurable scoring and authoritative MySQL eligibility checks. The student should be able to see not only who was 
recommended, but also which skills, domains, experience and career signals contributed to the ranking.
1.1 Recommendation feature goals

Identify potentially relevant alumni through Neo4j paths connecting Student, Mentor, Skill, Domain, Company and 
Department nodes. [B]

Evaluate candidates across skill similarity, domain relevance, relevant experience, career relevance and mentor 
quality. [PRD FR-09]

Check current account status, discoverability, capacity and other eligibility conditions in MySQL before a candidate 
reaches the final list. [PRD FR-09]

Display understandable reasons such as shared skills, matching domains, relevant experience and prior mentoring 
outcomes. [PRD FR-10]

Persist each recommendation run and its candidate scores so the team can compare changes over time and link a 
selected candidate to a later mentorship request. [PRD FR-10]
1.2 Recommended v1 design
Concern

and consistent with the blueprint. A recommendation is a candidate suggestion, not an automatic mentorship allocation.
1.3 What a recommendation is - and is not

3.2 Architecture principle
MySQL wins when stores disagree
Neo4j can find a mentor who is highly relevant but has already reached capacity. MySQL must exclude that mentor from the final 
response. Redis may return a previously computed candidate list, but the backend must still perform current eligibility checks 
before serving it as requestable.
4. Neo4j Recommendation Graph Model
Neo4j is used for relationship-oriented discovery, not as a second authoritative copy of the relational database. Use the 
same stable MySQL identifier on each graph node so the application can re-check each candidate in MySQL.

6. Filtering and Candidate Eligibility
Filtering must be separated from scoring. Filters decide whether a candidate can be shown or whether the student explicitly 
asked to restrict the search. Scoring decides how strongly each remaining candidate matches.
6.1 Three classes of filter
Class
What it does
Examples
A. Mandatory eligibility gate
Excludes mentors who cannot currently be 
recommended / cannot accept a mentee.
Inactive account; hidden profile; no remaining capacity; 
duplicate active student-mentor allocation; self-match.
B. Student-selected hard filter
Restricts results because the student explicitly 
selected a condition.
Specific domain; selected skill; company / industry;

C. Soft ranking signal
Does not automatically exclude a candidate;

Partial skill overlap; related domain; adjacent career

Do not confuse capacity with appointment availability
Capacity means whether the mentor can accept another mentee / allocation. A published time slot is appointment availability. Do 
not require an open slot for general mentor discovery unless the student explicitly asks for a date or booking window. Actual 
booking must separately revalidate the slot in MySQL.



Why capacity is a gate, not a reward score
The PRD names capacity as a recommendation dimension and separately requires candidates failing current MySQL capacity / 
eligibility checks to be excluded from final results. This design treats capacity as a binary eligibility gate. It avoids showing a full 
mentor as a low-scoring option that the student cannot actually request.
7.1 Overall score formula
Weighted score formula
OverallScore = (wS * SkillScore
             + wD * DomainScore
             + wE * ExperienceScore
             + wC * CareerScore
             + wQ * QualityScore) / (wS + wD + wE + wC + wQ)
Default: 0.30*S + 0.20*D + 0.15*E + 0.20*C + 0.15*Q
Each dimension score is normalized to the range 0-100. Since the default weights sum to 100, the result is also between 0 
and 100. If a dimension is genuinely unavailable, the scoring service may renormalize over the available dimensions, but 
the run must record which dimensions were missing and the effective denominator. Do not quietly treat missing data as a 
zero score.

8. Dimension Score Calculation
8.1 Skill similarity - 30%
The blueprint asks how many relevant student skills overlap with mentor expertise. The conceptual model already provides 
Student Skill and Mentor Skill relationships with proficiency and experience metadata.
Proposed skill coverage formula
Let K_s = skills recorded for the student.
For each student skill k, let r_k be its relevance weight (default 1).
Let e_mk be the mentor expertise strength for that skill, normalized 0..1.
SkillScore(m) = 100 * SUM(r_k * e_mk for k in K_s matched by m)
                      / SUM(r_k for k in K_s)
A possible proficiency normalization is `mentor_proficiency / maximum_proficiency`, capped to 1. Experience in a matched 
skill may be used to calibrate expertise strength if the team records a consistent scale. Avoid double-counting experience in 
the skill score and the separate experience dimension.
Example: if a student lists Python, Machine Learning and SQL with equal relevance, and a mentor has strong expertise in 
Python and Machine Learning but no SQL link, skill coverage is the two matched skills adjusted by expertise strength. The 
explanation should name the actual matched skills.
8.2 Domain relevance - 20%
The student’s domain-interest association contains priority / interest-level information. Mentor domain expertise contains an 
expertise level. This is a good place to use the relationship metadata rather than merely checking whether a domain name 
appears in a free-text biography.
Proposed domain alignment formula
Let D_s be the student preferred domains.
Let p_d be the student priority weight for domain d.
Let x_md be mentor expertise for domain d, normalized 0..1.
DomainScore(m) = 100 * SUM(p_d * x_md for matching domains)
                       / SUM(p_d for all student domains)
If the student sets Machine Learning as a higher-priority interest than Cloud Computing, a mentor specializing in Machine 
Learning contributes more strongly. Keep the scale for priority and expertise versioned so scores are comparable across 
runs.
8.3 Relevant experience - 15%
Use experience that is related to the matched skills / domains where possible. The Mentor Profile’s total experience years 
can be a fallback, but should not automatically be treated as relevant to every student goal.
Proposed experience normalization

RelevantYears(m) = weighted years of experience in matched

8.4 Career relevance - 20%
This dimension asks whether the mentor’s professional background fits the student’s career goal. The current conceptual 
model includes a student career goal and mentor job title, company and industry. For v1, map these to a small, controlled 
career-domain taxonomy.

These values are suggested rule bands, not measured probabilities. Store the mapping version and the evidence used. Do 
not infer relevance from employer prestige alone. A later semantic-search extension may add a semantic similarity signal, 
but the v1 rule-based score must remain understandable.
8.5 Mentor quality - 15%
Quality should use both historical ratings and outcomes while avoiding the mistake of treating one five-star review as 
definitive. A Bayesian-smoothed rating is a reasonable proposed approach for mentors with few reviews.
Proposed mentor-quality formula
AdjustedRating = (v / (v + m)) * MentorAverage
               + (m / (v + m)) * PlatformAverage
RatingScore = 100 * (AdjustedRating - 1) / 4   // 1..5 scale
QualityScore = 0.80 * RatingScore
             + 0.20 * CompletedOutcomeRate
Here `v` is the number of valid reviews and `m` is a configurable prior review count (example default: 5). `PlatformAverage` 
is the current platform mean rating. `CompletedOutcomeRate` may be defined as completed sessions divided by 
completed plus no-show sessions; participant-cancelled sessions should not be treated as a mentor failure by default. If 
outcome data is not reliable or unavailable, omit that part and renormalize the quality subscore. New mentors should 
receive a neutral prior and a “limited history” disclosure, not an automatic zero.
Do not call the score a success probability
An overall score of 91 means that the candidate has a strong relative fit under the selected criteria version. It does not mean the 
student has a 91% chance of a successful mentorship.

13. Neo4j Candidate Retrieval - Cypher Examples
Use Neo4j to return mentor ids and the graph evidence that caused each candidate to be discovered. The backend can 
merge results from separate skill, domain and professional-context traversals by mentor id; this keeps query logic readable 
and makes explanation evidence explicit.
13.1 Skill-based candidate discovery
Cypher A - shared skills
MATCH (s:Student {mysqlId: $studentId})
      -[:HAS_SKILL]->(sk:Skill)
      <-[hs:HAS_SKILL]-(m:Mentor)
RETURN
    m.mysqlId AS mentorId,
    collect(DISTINCT {
      skillId: sk.mysqlId,
      skillName: sk.name,
      proficiency: hs.proficiency,
      experienceYears: hs.experienceYears
    }) AS matchedSkills,
    count(DISTINCT sk.mysqlId) AS sharedSkillCount
ORDER BY sharedSkillCount DESC;
13.2 Domain-based candidate discovery
Cypher B - shared interest / expertise domains
MATCH (s:Student {mysqlId: $studentId})
      -[interest:INTERESTED_IN]->(d:Domain)
      <-[expertise:SPECIALIZES_IN]-(m:Mentor)
RETURN
    m.mysqlId AS mentorId,
    collect(DISTINCT {
      domainId: d.mysqlId,
      domainName: d.name,
      studentPriority: interest.priority,
      mentorExpertise: expertise.expertiseLevel
    }) AS matchedDomains
ORDER BY size(matchedDomains) DESC;
13.3 Professional-context discovery
Cypher C - company / industry evidence (only when relevant filters are used)
MATCH (m:Mentor)-[job:WORKS_AT]->(c:Company)
WHERE c.mysqlId IN $selectedCompanyIds
   OR c.industry IN $selectedIndustries
RETURN m.mysqlId AS mentorId,
       collect(DISTINCT {
         companyId: c.mysqlId,
         companyName: c.companyName,
         industry: c.industry,
         jobTitle: job.jobTitle,
         isCurrent: job.isCurrent
       }) AS careerEvidence;
13.4 Merge and de-duplicate candidates

The FastAPI discovery module collects mentorId values from the skill, domain and optional career traversals.

Merge by mysqlId and de-duplicate evidence lists by skillId / domainId / companyId.

Retain the graph evidence used to build score components and explanation text.

Pass only candidate ids and required feature evidence to the MySQL validation stage; do not treat graph properties as

14. MySQL Eligibility Validation and Final Ranking
After graph retrieval, validate current eligibility against MySQL. The PRD explicitly requires the final candidate list to

14.1 SQL-style eligibility template
Illustrative eligibility query - adapt names and status model to final schema
SELECT m.mentor_id, m.experience_years, m.capacity,
       u.account_status
FROM mentor_profile AS m
JOIN user_account AS u ON u.user_id = m.user_id
WHERE m.mentor_id IN (/* Neo4j candidate ids */)
  AND u.account_status = 'ACTIVE'
  AND m.is_discoverable = 1
  AND (
       SELECT COUNT(*)
       FROM mentor_allocation AS a
       WHERE a.mentor_id = m.mentor_id
         AND a.status = 'ACTIVE'
      ) < m.capacity
  AND NOT EXISTS (
       SELECT 1
       FROM mentor_allocation AS a2
       WHERE a2.mentor_id = m.mentor_id
         AND a2.student_id = :student_id
         AND a2.status = 'ACTIVE'

14.2 Score combination and ranking
Illustrative ranking expression for the v1 configuration
SELECT mentor_id,
       ROUND(
         0.30 * skill_score
       + 0.20 * domain_score
       + 0.15 * experience_score
       + 0.20 * career_score
       + 0.15 * quality_score, 2

FROM eligible_candidate_scores
ORDER BY total_score DESC,
         domain_score DESC,

15. Redis Recommendation Cache and Performance
Redis is a performance layer. The Application Architecture proposes caching recent recommendation results and popular 
mentor ranking views, using cache-aside, TTL and invalidation. The cache must remain rebuildable.
15.1 Suggested key design
Illustrative cache key / value
recommendation:v1:{student_id}:{filter_hash}:{criteria_version}
Example value:
{
  "run_id": 812,
  "mentor_ids": [104, 209, 311],
  "score_version": "mentor-match-v1",
  "generated_at": "2026-11-02T18:00:00Z",
  "profile_version": 17
}
Cache policy
Recommended behaviour
Key partitioning
Include student id, normalized filter hash and criteria version. Include profile / graph version where available.
TTL
Start with a short configurable TTL (example: 5-10 minutes); tune under test. This is a proposed value, not a source 
requirement.
Cache hit
Use cached candidate / feature data, but revalidate current MySQL eligibility before returning requestable cards.
Cache miss
Run graph discovery, SQL checks, scoring and history persistence; then cache a safe response payload.
Invalidation
Invalidate when student skills/interests/career goal, mentor profile/skills/domains, mentor capacity, ratings or catalogue 
mappings change.
Privacy
Do not cache private fields in a shared / publicly accessible keyspace; include authorization in the retrieval path.
15.2 Invalidation triggers
Committed MySQL event
Required secondary action
StudentProfileUpdated / StudentSkillsUpdated
Invalidate this student’s recommendation keys.
MentorProfileUpdated / MentorSkillsUpdated
Invalidate mentor-card keys and recommendation sets that may contain the mentor.
MentorDomainExpertiseUpdated
Invalidate graph projection and relevant recommendation keys.
MentorCapacityChanged / AllocationCreated / 
AllocationEnded
Revalidate candidate eligibility; invalidate relevant cached rankings.
MentorReviewCreated / SessionOutcomeRecorded
Refresh mentor-quality signals and cache entries.
SkillOrDomainCatalogueChanged
Refresh graph/catalogue projections and affected recommendation caches.
Cache is never booking authority
A cached recommendation can become stale after another student creates an allocation or a mentor changes capacity. Current 
MySQL must determine whether the mentor is still requestable. Booking slot correctness is handled by the separate atomic 
booking transaction, not by this recommendation cache.
16. Cross-Database Consistency and Event Processing
MySQL is strongly authoritative for business records, Redis is disposable cache / temporary state, and Neo4j is an 
eventually consistent projection. The application should not independently write to MySQL and Neo4j and assume both 
writes will succeed.

19.1 Data access

Only authenticated students may request recommendations for their own student profile unless an explicitly authorized



Implementation recommendation

A recommendation score is only as reliable as its profile evidence. The system should record data-quality flags such as

explanation language and internal evaluation; they should not silently alter score meaning.

21.3 Recommended viva explanation
How to explain the recommendation engine
“We use Neo4j to discover mentor candidates through shared skills, domains and professional connections. We then validate 
each candidate in MySQL because MySQL owns current account status and mentorship capacity. Eligible candidates receive a 
transparent weighted score across skill similarity, domain relevance, experience, career relevance and mentor quality. We save 
each run and its explanations in MySQL, and use Redis only to cache recent results. Selecting a recommendation creates a 
mentorship request; it does not create an allocation until the mentor accepts.”

23. Glossary
Term
Meaning
Candidate generation
Finding a pool of mentor ids through graph paths.
Eligibility gate
A mandatory test that removes candidates who are not currently requestable.
Dimension score
A normalized 0-100 score for one matching factor.
Weighted contribution
Dimension score multiplied by its configured weight.
Criteria version
A named and immutable set of weights and score parameters.
Recommendation Run
One recorded calculation for a particular student and filter/input snapshot.
Recommended Mentor
A candidate result attached to one recommendation run.
Projection
A graph representation derived from authoritative MySQL data.
Outbox
A durable MySQL event row written in the same transaction as source changes.
Cache-aside
Application checks cache first; on a miss it computes from source and then caches.
Cold start
A profile or mentor with limited matching / outcome history.

Final design statement

score to rank eligible candidates, evidence-based explanations to build student trust, and persistent recommendation history to 
evaluate what happened after selection.
