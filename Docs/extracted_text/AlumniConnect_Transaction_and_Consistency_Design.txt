external notification providers are updated only after commit and must never decide whether a booking or

AlumniConnect is a modular monolith backed by polyglot persistence. FastAPI is the single logical application

availability, bookings, sessions, feedback, reviews, notifications and audit history. Redis accelerates selected
reads and stores temporary state. Neo4j supports relationship-oriented mentor discovery.

1.2 Consistency model
• Strong transactional consistency: all business invariants that must hold immediately are enforced in MySQL
transactions and constraints.
• Eventual projection consistency: Redis invalidation and Neo4j updates may lag after commit, but they are
retryable and do not override MySQL.
• Read freshness: cached display data may have bounded staleness; booking and allocation decisions always
re-read and validate current MySQL rows.
NON-NEGOTIABLE
A cache hit, graph path, notification status or front-end calendar state is never proof that a business transition is
allowed. The final validation occurs in the authoritative MySQL transaction.

2. Transaction model and transaction boundaries
A transaction is a logical unit of database work. Its operations are treated as one all-or-nothing change. For
AlumniConnect, transaction boundaries are defined around business actions, not around individual SQL
statements or HTTP requests.
2.1 What belongs inside one transaction
A state-changing operation should include all authoritative writes needed to make the business action true,
including the related outbox row and audit entry when those are part of the operation. If any required write or
validation fails, the transaction rolls back.
INCLUDE IN THE SAME MYSQL TRANSACTION
DO NOT INCLUDE IN THE MYSQL TRANSACTION
Business row updates and inserts.
Sending email, SMS, push notification or invoking a remote
provider.
State/status transition and corresponding history/audit write.
Redis DEL / INCR or cache population.
Required allocation, booking, availability or session changes.
Neo4j node/relationship projection.
Outbox event describing committed side effects.
Long-running report generation or unrelated API calls.
Database uniqueness / FK / check enforcement.
User think time, UI confirmation or network waits.

2.3 Do not split one business action into multiple commits
For example, creating a booking in one transaction and marking the availability slot BOOKED in a second
transaction creates a failure window. If the application crashes between commits, the booking and slot can
disagree. The booking row, slot transition, planned session record (where the chosen workflow creates it
immediately) and outbox event must be committed together.
DESIGN TEST
For each business action, ask: “What exact durable state must exist if this action is reported successful?” All of
that state belongs in one transaction.

3.1 Atomicity - rollback examples
• Allocation insert fails after request acceptance was attempted: request must remain PENDING; no acceptance
notification event exists.
• Booking insert succeeds but slot update fails or affects zero rows: roll back the booking and outbox event.
• Session outcome update succeeds but outbox insert fails: roll back the outcome update too.

Isolation is delivered through the configured InnoDB isolation level together with explicit locking reads and

deployed InnoDB durability settings and demonstrate persistence after restart rather than claiming durability
based only on an API success response.

outside the lock-holding transaction, and records delivery status separately.

5.3 Acceptance race
Two concurrent acceptance attempts for the same request must not create two allocations. One transaction
locks the request, validates PENDING, inserts the allocation and updates the request. The second waits; after
lock acquisition it re-reads and sees ACCEPTED, then returns a conflict/already-processed result. A UNIQUE
constraint on allocation.request_id is the final database backstop.
REQUIRED RESULT
Exactly one ACTIVE allocation; request status ACCEPTED; one committed outbox intent. The competing attempt
must not create a second allocation or notification.
6. Reject, cancel request and publish availability
6.1 Reject or cancel a pending request
Reject and cancel are separate actor-authorized transitions from PENDING. The addressed mentor rejects; the
student who opened the request cancels. Both operations lock the request and re-check the status inside the
transaction. Rejected and cancelled rows remain in history.

6.2 Publish mentor availability
Source terminology note: the Business Rules Catalogue describes the initial slot state as OPEN, while one
Workflow SQL example uses AVAILABLE. The physical schema must choose one canonical status value. Code
examples in this specification use OPEN. Availability publication should be serialized per mentor. Lock the
mentor profile row before checking for overlapping active slots and inserting the new slot(s). This parent-row
lock prevents two simultaneous publication calls from each observing “no overlap” and inserting conflicting time
ranges.
• Validate start_at < end_at and interpret/store time instants consistently (the catalogue recommends UTC).
• Check mentor account/profile is active and permitted to publish slots.
• Check no overlapping active availability exists unless group/parallel sessions are explicitly supported.
• Do not delete historical slots that have bookings; block, expire or otherwise preserve history.
6.3 Overlap predicate
The business-rules catalogue uses half-open time intervals [start_at, end_at). Two appointments overlap when
existing.start_at is earlier than the requested end and existing.end_at is later than the requested start. Thus
10:00–10:30 and 10:30–11:00 are adjacent, not overlapping.

7. Booking transaction - critical consistency path
Booking is the most critical transaction in AlumniConnect. Two students may try to reserve one mentor slot at
nearly the same time. A calendar preview is only a read hint. MySQL must decide the result by locking and
validating current rows inside the booking transaction.
FastAPI
authorize + validate
MySQL TX
lock guard rows
MySQL TX
insert booking + slot
Outbox row
same commit
Commit
confirmed result
Redis / Neo4j / email are not called while the InnoDB locks are held.
7.1 Preconditions
• The actor is the student associated with the active allocation.
• The allocation is ACTIVE and the selected slot belongs to the same mentor.
• The slot exists, is OPEN/AVAILABLE and starts in the future.
• The student and mentor have no overlapping CONFIRMED appointment.
• Mentor capacity and any domain/business-specific booking policy are satisfied.
• The request is not a duplicate retry; idempotency key and request fingerprint are consistent.
7.2 Fixed lock order
1 Student profile
lock / re-read
2 Mentor profile
lock / re-read
3 Allocation
lock / re-read
4 Availability slot
lock / re-read
5 Booking / Session
lock / re-read
Use the same order in every procedure that touches these resources.
The Business Rules Catalogue recommends a consistent order such as student profile → mentor profile →
allocation → availability slot → booking/session. All procedures that touch these shared resources must use the
same order. If a procedure starts from booking_id, it may perform a non-locking lookup to discover the involved
IDs, then acquire locks in the canonical order and re-read the booking row before mutating it.
7.3 Why lock the participant profile rows?
Locking only the availability slot serializes two users competing for the exact same slot. It does not prevent one
student from booking two overlapping slots with two different mentors, nor does it prevent one mentor’s
separate slots from being booked at overlapping times. The student and mentor profile rows act as serialization
points for all booking operations involving those participants.

9.2 Cancellation policy decisions
The supplied documents do not set a precise cancellation cutoff or guarantee that every cancellation reopens
the slot. Those are configurable product decisions. The database procedure must apply the final policy
consistently and preserve the original booking and its audit history.
• Whether a slot is reopened depends on timing and the approved cancellation rule.
• A confirmed booking cannot be edited in place to a different participant or slot.
• Rescheduling should create a replacement booking linked to the original; the original becomes
CANCELLED/RESCHEDULED according to the agreed state model.
9.3 Reschedule as one atomic operation
The safest approach is to reserve the new slot and transition the old booking in one transaction. Lock both
participant rows, both availability rows in ascending stable ID order, then the original booking. If the new slot
cannot be reserved, roll back so the original booking remains confirmed. Preserve a
rescheduled_from_booking_id link for auditability.
SOURCE-DEFINED INVARIANT
The business rules catalogue says the original booking history must be preserved; rescheduling should not
silently overwrite participant, slot or timestamp fields.

11. InnoDB locking strategy
Use row-level locks for the records that represent resources being changed or whose state/capacity must remain

11.2 Locking rules
• Use the same order in create, cancel and reschedule procedures. Sort multiple rows of the same type by
immutable ID before locking them.
• Re-read state after acquiring the lock. A value read before locking is only a discovery hint.
• Keep transactions short. Do not call Redis, Neo4j, email providers or remote APIs while holding database locks.
• Use indexes that make locking reads selective; an unsuitable range scan can lock more records than intended.
• Use constraints as backstops even when procedures lock rows correctly.
11.3 Two-phase locking and deadlocks
The database may hold locks until commit/rollback. Two-phase locking can provide conflict-serializable
behaviour, but it does not eliminate deadlocks. Deadlocks can occur when two transactions wait in a cycle,
especially when they acquire shared resources in different orders. InnoDB detects a deadlock and rolls back a
victim; the application must retry the entire transaction when it is safe.

12.1 Why overlap checking needs a parent-row lock
A normal overlap query can return zero rows to two concurrent transactions. If they each insert a conflicting
appointment, a check-then-insert race has occurred. Locking only existing booking rows is insufficient when the
set is empty. The design therefore locks a stable parent row (student_profile and mentor_profile) as the
serialization point, and every booking writer follows that convention.

16. Transactional outbox pattern
The transactional outbox solves the dual-write problem. FastAPI must not commit a business row and then
separately “hope” it can publish a notification or graph/cache update. Instead, the business transaction inserts a
durable event intent in MySQL. The worker processes only committed outbox rows.

same InnoDB transaction

Worker

If SQL rolls back, no event exists. If a worker fails, the committed event remains retryable.

17.2 Delivery is at-least-once; make consumers idempotent
A worker may crash after a provider accepts a notification but before MySQL is updated to SENT. On restart the
event can be retried. Exactly-once delivery across an external provider and MySQL is generally not guaranteed
by the outbox alone. Design for at-least-once attempts and deduplicate using provider idempotency support or a
stable event/recipient key.

18.1 Redis invalidation idempotency
DEL of a missing key is naturally safe to replay. INCR is not idempotent: a repeated event can advance an epoch
more than once. If epoch correctness depends on a single application of the event, use an event marker and
invalidation in one Redis Lua script/atomic operation, or use a deterministic version value from the committed
aggregate version. Do not write a deduplication marker in a separate command before the invalidation.
18.2 Neo4j projection
Graph updates should use stable MySQL IDs and idempotent MERGE/upsert operations. A failed or lagging
projection is a recommendation freshness issue, not a reason to skip MySQL status, privacy, capacity or
eligibility checks. Redis and Neo4j may be rebuilt from MySQL/outbox history according to the recovery plan.
18.3 Cache consistency boundary
The Redis Design Specification defines cache-aside, bounded TTL, targeted DEL, cache epochs and event
mapping. It also says authorization must run for cache hits and availability preview must never confirm a
booking. This document treats those rules as downstream consistency obligations of the outbox worker.

Appendix C. Key terms
TERM
MEANING IN THIS DESIGN
ACID
Atomicity, Consistency, Isolation and Durability - transaction properties.
Aggregate / guard row
A stable parent row locked to serialize operations that affect a shared capacity or overlap rule.
Deadlock
A cycle of transactions waiting for one another’s locks; InnoDB rolls back a victim.
Idempotency key
A client-supplied unique token used to recognize a retry of the same logical request.
InnoDB row lock
A lock acquired by a transaction on selected records/index records to coordinate concurrent work.
Outbox
A durable event row inserted in the same transaction as the business change.
Phantom / overlap race
A concurrent insert creates a row matching a predicate that another transaction previously checked
as empty.
Projection
A derived, rebuildable representation in Redis or Neo4j that is not authoritative business state.
Serialization point
A row/resource whose lock forces competing operations to take turns for a shared invariant.
Two-phase locking
A locking protocol in which locks are acquired before release; helps provide serializable conflict
behaviour but does not eliminate deadlocks.
Final design principle
The strongest version of AlumniConnect is not the version that puts every action into Redis, Neo4j or a separate
service. It is the version that gives each database a clear responsibility, defines exactly where each business
transaction begins and ends, protects its invariants under concurrency, and makes every secondary effect
durable and retryable.
FINAL RULE
MySQL commits the business truth. The outbox records what must happen next. Workers deliver and project after
commit. Redis and Neo4j accelerate discovery, but never override the committed relational state.
