1. Model scope and reading guide
This is a conceptual ER model: it describes the platform domain and its business relationships, not the final physical MySQL schema. Entity identifiers and example attributes are included to make
each concept understandable. Data types, indexes, SQL column definitions and implementation-specific foreign-key names are intentionally omitted.

How to read a relationship: In “Department 1 — 0..* Student Profile”, one department may be associated with many student profiles, while each student profile references exactly one primary
department. Read the endpoint cardinality next to the entity at that end of the line.
Important architecture boundary: MySQL owns authoritative identities, profiles, requests, allocations, bookings, sessions, feedback and reviews. Redis contains rebuildable caches and temporary
state; Neo4j contains a relationship-oriented projection for recommendations. Redis and Neo4j are storage technologies, not additional business entities in this conceptual ER diagram.

8. Business rules that constrain the ER model
These rules turn the conceptual relationships into behaviours the application must preserve. They should later become database constraints, transaction rules, API validations and test cases where
appropriate.
Rule
Requirement
BR-01 - Account identity
Each account has one common User identity. Student and mentor information belongs in separate profile entities, not duplicated login records.
BR-02 - Role separation
The model assigns one primary role to each user: Student, Mentor or Administrator. The blueprint does not specify multi-role accounts; a UserRole associative entity
would be needed if multiple roles per account are required.
BR-03 - Profile cardinality
A User may have zero or one Student Profile and zero or one Mentor Profile. An Administrator can therefore exist without either profile.
BR-04 - Skills and domains
Student Skill, Mentor Skill, Student Domain Interest and Mentor Domain Expertise each resolve a many-to-many association. A profile-skill or profile-domain pair
should not be duplicated.
BR-05 - Recommendation history
A Recommendation Run may return many Recommended Mentor candidates. Candidate rank, score and explanation are preserved per run so later runs do not
erase prior results.
BR-06 - Request lifecycle
A Mentorship Request progresses through Pending, Accepted, Rejected or Cancelled. Rejected and cancelled requests remain available for history and analytics.
BR-07 - Allocation creation
A request results in at most one Mentor Allocation. Acceptance verifies that the request is still pending, checks mentor capacity, prevents duplicate active allocations
and commits request status plus allocation atomically.
BR-08 - Availability ownership
Every Mentor Availability slot belongs to one Mentor Profile. A slot can be booked at most once.
BR-09 - Booking correctness
Before confirming a booking, validate the slot is still available, the student has no overlapping appointment, mentor capacity is respected, the relevant
request/allocation is valid, and the submission is not a duplicate.
BR-10 - Transactional booking
Booking confirmation must be atomic. Concurrent attempts for the same slot must not both succeed. MySQL/InnoDB is authoritative; Redis cache must never decide
availability.
BR-11 - Booking vs session
A booking is a plan. A session is the actual offline meeting. A confirmed booking may produce at most one session; a cancelled booking need not produce one.
BR-12 - Session lifecycle
A session can be Scheduled, Completed, Cancelled or No-show. The system preserves session history and mentor-entered topics, assessed skills, performance
observations, improvement areas and next steps.
BR-13 - Feedback eligibility
Feedback cannot be submitted before a session has taken place. Only the actual student or mentor participants may author session feedback.
BR-14 - Mentor review uniqueness
A student can submit at most one mentor review per completed session. The review references the session, student author and mentor being reviewed.
BR-15 - Notification events
Requests, decisions, booking confirmations/cancellations, reminders and feedback events can produce notifications for the appropriate participants.
BR-16 - Reliable notification delivery
Write an outbox event in the same MySQL transaction as the business change. A background worker later delivers it; this avoids sending a notification for a
rolled-back operation.
BR-17 - Audit history
Important status and data changes should be auditable. An audit record may have a user actor or be system-generated.
BR-18 - Source of truth
MySQL is authoritative. Redis stores temporary/rebuildable values. Neo4j is a recommendation projection and may be briefly stale; booking and allocation eligibility
must be revalidated in MySQL.

10. Explicit modelling assumptions and open decisions
The blueprint defines the business domain and several cardinalities, but it does not specify every participation constraint. The following choices make the ERD implementable without claiming that
they were all explicitly fixed in the blueprint.
ID / decision
Assumption or open decision
A1 - Primary role
One primary Role is assigned to each User. If users must act as both student and mentor under one account, introduce UserRole (M:N) or formalise a dual-profile rule.
A2 - Primary department
Each Student Profile and Mentor Profile has one primary Department. If multiple degrees/departments must be represented, introduce StudentDepartment and
MentorDepartment associative entities.
A3 - Current company
Mentor Profile has zero or one current Company. Prior employment history is outside this model; add MentorEmployment if needed.
A4 - Booking authorisation
Booking may be associated with zero or one Mentor Allocation in this conceptual model. The implementation must define whether a valid accepted request alone can
authorise a one-off booking.
A5 - Availability slot
Every Booking reserves exactly one availability slot; a slot can be reserved by at most one Booking. Slot duration and time-zone rules are implementation details.
A6 - One student per session
The current model assumes one student and one mentor per booking/session. Group mentoring or panel interviews would require participant association entities.
A7 - One review per session
The one-review maximum assumes a single student participant in each session. If group sessions are later supported, uniqueness must be per student-session pair.
A8 - Notification fan-out
One outbox event can produce multiple notifications, for example one to the student and one to the mentor. Each notification has exactly one recipient.
A9 - System audit actor
Audit Log actor is optional so system-generated events can be represented without inventing a human user.
A10 - Semantic vector search
Vector embeddings and vector indexes are an optional Phase 2 capability and are not included as entities in this core conceptual ER model.

What it does not own

12. Coverage and implementation hand-off
This model gives the team a stable conceptual starting point for the next DBMS artefacts: an ER diagram review, relational schema mapping, functional-dependency analysis, normalisation, SQL
DDL, constraints, indexes, transaction workflows and test data. The blueprint recommends a modular monolith: business modules may be separated in code, while the primary relational data remains
in one MySQL database.
