01 / ORIENTATION
Document guide and modelling conventions
This document specifies the operational lifecycle of AlumniConnect. It complements the Product Requirements 
Document and Conceptual ER Diagram; it does not replace the logical schema or final application API contract.
Scope covered

Student discovers a mentor and submits a mentorship request.

Mentor accepts or rejects; acceptance creates a mentor allocation in the same SQL transaction.

Mentor publishes availability; student books an eligible slot through an atomic operation.

A planned booking is distinguished from the actual offline mentorship/mock interview session.

Participants submit session feedback; a student may submit a mentor review after a completed session.

Business events are stored in a transactional outbox and delivered asynchronously.

MySQL triggers and procedures protect transitions, record audit history, and centralise critical database 
operations.

Important scope boundary
The blueprint uses a modular monolith. MySQL is the authoritative source of truth for identity, requests, 
allocations, availability, bookings, sessions, feedback and audit data. Redis is a cache/temporary-state layer; 
Neo4j is a graph projection for discovery. Neither Redis nor Neo4j should approve or commit a booking.

Business rules

A submitted request enters PENDING. The blueprint explicitly lists the resulting states as Accepted, Rejected or 
Cancelled.

An accepted request can create at most one allocation.

Rejected and cancelled requests remain in history; do not delete them to represent a decision.

The mentor accepting the request must be the mentor to whom the request was addressed.

The acceptance operation must check capacity and prevent duplicate active allocations.
Design note
The blueprint does not define a Draft state, expiry period, resubmission policy or a student withdrawal path 
after acceptance. Do not silently add these states. Record them as product decisions if the team wants them.

04 / ALLOCATION STATE MODEL
Mentor allocation lifecycle
Figure 3. Proposed allocation lifecycle. ACTIVE is the immediate result of accepting a request; end states are recommended extensions.
What an allocation represents
An allocation is the durable relationship between one student and one mentor after the mentor accepts a request. It 
is not the request itself and it is not an individual booked session. One allocation can support multiple sessions over 
time.

Booking confirmation guards

The mentor slot is still available at the moment of confirmation.

The student has no overlapping confirmed appointment.

The mentor has no overlapping confirmed appointment and has not exceeded the allowed capacity.




Recommended status treatment
The blueprint explicitly refers to Booking Confirmed and Booking Cancelled notifications, but it does not specify a 
full booking status enum. A minimal design can use CONFIRMED -> CANCELLED. The slot may use AVAILABLE -> 
BOOKED, and optionally WITHDRAWN before booking. Whether cancellation returns a slot to AVAILABLE must be 
decided as a cancellation policy; do not infer it automatically.

06 / TRANSACTION AND CONCURRENCY
Atomic booking - detailed sequence
Figure 5. Booking succeeds only after all guards pass. Failure rolls back the entire write set.
Why this operation must be atomic
Consider two students selecting the same mentor slot at nearly the same time. If both read AVAILABLE before 
either writes, a simple application-level check can allow both to proceed. The booking routine must lock the 
relevant rows, re-check current state while holding those locks, and commit the slot change and booking row 
together.

Concurrency recommendation
Every code path that creates or changes a booking must acquire guard locks in the same order. Keep transactions 
short. Add a UNIQUE constraint on availability_id for active/one-time slot consumption where your schema 
supports it. Handle a deadlock by retrying the complete transaction, not by continuing halfway through it.
Overlap predicate
existing.start_at < requested_end
AND existing.end_at > requested_start
AND existing.booking_status = 'CONFIRMED'
This predicate detects time-range intersections. Apply it for the student and the mentor. The conflict check is only 
safe when performed under the agreed lock strategy; a plain SELECT followed by INSERT is not sufficient under 
concurrent load.

08 / POST-SESSION RECORDS
Feedback and mentor review lifecycle
Figure 7. Feedback and rating/review are distinct business concepts.
Session feedback
The blueprint allows structured feedback from either actual participant. Example dimensions include 
communication, helpfulness, technical preparation and session notes. A feedback record must reference the actual 
session and its author.
Mentor review
A mentor review is the student’s rating and written review of the mentor after a completed session. It is not simply 
another field inside generic feedback.

Suggested lifecycle
A simple model is DRAFT (optional client-side only) -> SUBMITTED (persistent). The supplied blueprint does not 
define a separate review moderation, edit, publication or dispute state machine. Add such states only if the team 
decides they are required.

Outbox pattern
6.
The procedure performs the business change and inserts an outbox event within the same MySQL transaction.
7.
If the business transaction rolls back, the outbox event rolls back too; no false notification is delivered.
8.
A separate worker polls unprocessed events, claims one safely, sends the message and marks it SENT.
9.
Temporary failures are retried with backoff; permanent failures are moved to a dead-letter state for inspection.

Critical implementation rule
Do not send email, push notifications or call a third-party API from a database trigger. The trigger/procedure 
writes a durable event record; the worker performs external delivery after commit.

10 / DATABASE AUTOMATION
Trigger design for AlumniConnect
A trigger is a named database object that automatically executes in response to an INSERT, UPDATE or DELETE on a 
table. MySQL row triggers can run BEFORE or AFTER the row operation and use OLD and NEW values. The course 
material introduces triggers as a mechanism for enforcing integrity rules, monitoring updates and maintaining 
derived information.

What should not be done in triggers

Do not put the entire booking transaction in a trigger. Stored procedures / backend transaction orchestration 
are clearer for multi-row business workflows.

Do not use triggers to send email or call HTTP services. Triggers are for database-side work.

Do not issue COMMIT, ROLLBACK or START TRANSACTION inside a trigger. The trigger runs as part of the 
statement’s transaction.

Avoid duplicating the same outbox event in both a trigger and a stored procedure. Choose one owner for event 
creation.

Do not rely on triggers alone to prevent concurrent slot claims; use transaction locks and unique constraints.

11 / MYSQL IMPLEMENTATION EXAMPLES
Trigger examples - state guards and audit
The following examples assume MySQL 8.x, InnoDB and the conceptual table names shown in this document. 
Rename columns to match the final logical schema. Keep the trigger small, deterministic and limited to database-
local validation/audit work.
A. Reject an invalid mentorship-request transition
DELIMITER $$
CREATE TRIGGER trg_request_state_guard
BEFORE UPDATE ON mentorship_request
FOR EACH ROW
BEGIN
    IF OLD.status <> NEW.status
       AND OLD.status <> 'PENDING' THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'A decided request cannot be changed';
    END IF;
    IF OLD.status = 'PENDING'
       AND NEW.status NOT IN ('PENDING', 'ACCEPTED',
                              'REJECTED', 'CANCELLED') THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Invalid mentorship request state';
    END IF;
END$$
DELIMITER ;
This guard prevents an accepted/rejected/cancelled request from being silently moved back to pending or another 
state. The stored procedure still checks actor identity and business eligibility because a trigger should not replace 
application authorization.
B. Audit a request status change
DELIMITER $$
CREATE TRIGGER trg_request_status_audit
AFTER UPDATE ON mentorship_request
FOR EACH ROW
BEGIN
    IF OLD.status <> NEW.status THEN
        INSERT INTO audit_log
          (entity_type, entity_id, action_name,
           old_value, new_value, changed_at)
        VALUES
          ('MENTORSHIP_REQUEST', NEW.request_id,
           'STATUS_CHANGED', OLD.status, NEW.status,
           CURRENT_TIMESTAMP);
    END IF;
END$$
DELIMITER ;
For production-quality auditing, extend the table with actor_user_id, request correlation ID, source module and 
structured JSON snapshots. The backend should set a trusted actor context for the database connection; reset it 
correctly when returning connections to a pool.

11B / MYSQL IMPLEMENTATION EXAMPLE
Trigger example - session lifecycle guard
C. Guard the mentorship-session lifecycle
DELIMITER $$
CREATE TRIGGER trg_session_state_guard
BEFORE UPDATE ON mentorship_session
FOR EACH ROW
BEGIN
    IF OLD.session_status <> NEW.session_status
       AND OLD.session_status <> 'SCHEDULED' THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Terminal session state cannot be changed';
    END IF;
    IF OLD.session_status = 'SCHEDULED'
       AND NEW.session_status NOT IN
           ('SCHEDULED', 'COMPLETED', 'CANCELLED', 'NO_SHOW') THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Invalid session state';
    END IF;
END$$
DELIMITER ;
This guard follows the lifecycle stated in the blueprint. Treat terminal outcomes as immutable in ordinary user 
workflows; if administrators must correct a mistaken outcome, use a separate privileged correction routine that 
records who changed it and why.
Trigger deployment checklist

Create triggers through version-controlled database migrations.

Inspect definitions using SHOW CREATE TRIGGER and keep trigger names unique and descriptive.

Test multi-row INSERT/UPDATE statements because row triggers execute once per affected row.

Verify that trigger writes roll back with the statement if a later operation in the same transaction fails.

Avoid duplicate audit/outbox rows when procedures and triggers both touch the same event.

13 / TRANSACTIONAL REQUEST DECISION
Procedure example - accept or reject a request
This is a reference template, not a drop-in migration. It assumes request_id, student_id, mentor_id, status and 
mentor_profile.max_active_mentees. Add exact schema names, audit columns, actor authentication and business 
policy from your final ER-to-relational mapping.
DELIMITER $$
CREATE PROCEDURE sp_respond_to_mentorship_request(
    IN p_request_id BIGINT,
    IN p_mentor_id  BIGINT,
    IN p_decision   VARCHAR(10),
    IN p_reason     VARCHAR(500)
)
proc: BEGIN
    DECLARE v_found INT DEFAULT 1;
    DECLARE v_student_id BIGINT;
    DECLARE v_request_mentor_id BIGINT;
    DECLARE v_status VARCHAR(20);
    DECLARE v_capacity INT;
    DECLARE v_active_count INT;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_found = 0;
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;
    IF p_decision NOT IN ('ACCEPT', 'REJECT') THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Decision must be ACCEPT or REJECT';
    END IF;
    START TRANSACTION;
    SELECT student_id, mentor_id, status
      INTO v_student_id, v_request_mentor_id, v_status
      FROM mentorship_request
     WHERE request_id = p_request_id
     FOR UPDATE;
    IF v_found = 0 THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Mentorship request not found';
    END IF;
    IF v_request_mentor_id <> p_mentor_id THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Only the assigned mentor may decide';
    END IF;
    IF v_status <> 'PENDING' THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Request is no longer pending';
    END IF;
    IF p_decision = 'ACCEPT' THEN
        SET v_found = 1;
        SELECT max_active_mentees
          INTO v_capacity
          FROM mentor_profile
         WHERE mentor_id = p_mentor_id
         FOR UPDATE;
        IF v_found = 0 THEN
            SIGNAL SQLSTATE '45000'
              SET MESSAGE_TEXT = 'Mentor profile not found';
        END IF;
        SELECT COUNT(*) INTO v_active_count
          FROM mentor_allocation
         WHERE mentor_id = p_mentor_id
           AND status = 'ACTIVE';
        IF v_active_count >= v_capacity THEN
            SIGNAL SQLSTATE '45000'
              SET MESSAGE_TEXT = 'Mentor capacity reached';
        END IF;

            (p_request_id, v_student_id, p_mentor_id,
             'ACTIVE', CURRENT_TIMESTAMP);
        UPDATE mentorship_request
           SET status = 'ACCEPTED', decided_at = CURRENT_TIMESTAMP,
               decision_reason = p_reason
         WHERE request_id = p_request_id;
        INSERT INTO notification_outbox
            (event_type, aggregate_type, aggregate_id, payload, status)
        VALUES
            ('REQUEST_ACCEPTED', 'MENTORSHIP_REQUEST', p_request_id,
             JSON_OBJECT('student_id', v_student_id,
                         'mentor_id', p_mentor_id), 'PENDING');
    ELSE
        UPDATE mentorship_request
           SET status = 'REJECTED', decided_at = CURRENT_TIMESTAMP,
               decision_reason = p_reason
         WHERE request_id = p_request_id;
        INSERT INTO notification_outbox
            (event_type, aggregate_type, aggregate_id, payload, status)
        VALUES
            ('REQUEST_REJECTED', 'MENTORSHIP_REQUEST', p_request_id,
             JSON_OBJECT('student_id', v_student_id,
                         'mentor_id', p_mentor_id), 'PENDING');
    END IF;
    COMMIT;
END$$
DELIMITER ;
What this procedure demonstrates
IN parameters, row-level locking, state validation, capacity validation, conditional INSERT/UPDATE, JSON event 
payloads, one transaction, exception rollback and RESIGNAL. It implements the blueprint’s requirement that 
request acceptance, allocation creation and notification-event recording succeed or fail together.

14 / TRANSACTIONAL SCHEDULING
Procedure example - atomic booking
The booking routine is the most concurrency-sensitive operation in AlumniConnect. The template below shows the 
required control sequence. The exact SQL for overlap checks must match your final slot representation and 
indexes.
-- PSEUDOCODE-LEVEL MYSQL ROUTINE TEMPLATE
-- Use one deterministic lock order in every booking/cancellation path.
START TRANSACTION;
-- 1. Serialise requests for the same student.
SELECT student_id
  FROM student_profile
 WHERE student_id = p_student_id
 FOR UPDATE;
-- 2. Serialise capacity / overlapping-mentor checks.
SELECT mentor_id, max_active_mentees
  FROM mentor_profile
 WHERE mentor_id = p_mentor_id
 FOR UPDATE;
-- 3. Lock the selected availability row.
SELECT mentor_id, start_at, end_at, status
  FROM mentor_availability
 WHERE availability_id = p_slot_id
 FOR UPDATE;
-- 4. Validate slot is still AVAILABLE and is in the future.
-- 5. Validate allocation is ACTIVE (where booking requires allocation).
-- 6. Check confirmed overlap for this student.
--    existing.start_at < requested_end
--    AND existing.end_at > requested_start
-- 7. Check confirmed overlap for this mentor.
-- 8. Validate mentor capacity and request idempotency.
INSERT INTO booking (..., booking_status, ...)
VALUES (..., 'CONFIRMED', ...);
UPDATE mentor_availability
   SET status = 'BOOKED'
 WHERE availability_id = p_slot_id
   AND status = 'AVAILABLE';
-- Check ROW_COUNT() = 1; otherwise SIGNAL and ROLLBACK.
INSERT INTO notification_outbox (...)
VALUES (..., 'BOOKING_CONFIRMED', ..., 'PENDING');
COMMIT;
-- On any SQL exception: ROLLBACK; RESIGNAL;
Mandatory booking constraints

UNIQUE(availability_id) on booking if each offered slot can only be consumed once.

Foreign keys from booking to student, mentor, availability and (where required) allocation.

CHECK end_at > start_at; CHECK booking purpose is one of the supported types.

Index booking(student_id, booking_status, start_at, end_at).

Index booking(mentor_id, booking_status, start_at, end_at).

An idempotency key with a unique constraint prevents retrying the same client submission from creating 
duplicate bookings.

-- UNIQUE(session_id, student_id) prevents duplicate review.

-- Or INSERT INTO mentor_review (...) for the rating/review record.
-- Insert FEEDBACK_SUBMITTED outbox event if required.
COMMIT;

17 / UNIT 4 INTEGRATION
Transactions, ACID and concurrency
ACID applied to request acceptance
Property
How AlumniConnect demonstrates it
Atomicity
Request state update + allocation insert + outbox event 
commit together or all roll back.
Consistency
Foreign keys, unique constraints, allowed status transitions 
and mentor capacity rules remain valid.
Isolation
Concurrent acceptances / bookings cannot read stale 
eligibility and both claim the same resource.
Durability
Once committed, the request decision, allocation, booking and 
outbox event persist after failure.
Locking and deadlocks

Use SELECT ... FOR UPDATE for rows that will be changed or whose availability/capacity must be protected.

Keep the transaction short: do not call external notification providers while holding database locks.

Lock rows in a consistent order across procedures to reduce circular waits.

A deadlock is a cycle of transactions waiting for each other. InnoDB detects deadlocks and rolls back a victim; 
the application should retry the entire transaction with bounded retries and jitter.

Use appropriate indexes so a locking read does not scan and lock far more rows than needed.
Suggested transaction boundaries
Operation
One transaction must include
Accept request
Lock request; validate mentor; lock mentor capacity; insert 
allocation; update request; insert outbox event.
Create booking
Lock student, mentor and availability; validate overlaps and 
capacity; insert booking; change slot; insert outbox event.
Cancel booking
Lock booking; authorise actor; update booking; apply slot-
release rule; insert outbox event.
Record outcome
Lock session; validate SCHEDULED; write outcome and notes; 
insert outbox event.
Submit feedback
Lock / validate session; validate participant and review 
uniqueness; insert feedback/review; insert outbox event.
