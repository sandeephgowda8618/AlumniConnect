Alumni–Student Mentorship Platform: 
DBMS Project Blueprint 
My recommendation is to develop this as a production-style Alumni–Student Mentorship and 
Mock Interview Platform, with database engineering as its main strength. 
The goal should be bigger than building a website where students find alumni and book 
interviews. Your application should demonstrate that you understand: 
●​ How to design a relational database from business requirements. 
●​ How to enforce data integrity through constraints and transactions. 
●​ How to write complex and efficient SQL queries. 
●​ How to manage concurrent users and prevent inconsistent updates. 
●​ How to use key-value databases for low-latency access. 
●​ How to represent connected data in a graph database. 
●​ How to combine multiple database technologies without creating inconsistent data. 
I reviewed your four-unit DBMS course outline and the existing Alumni Mentor Allocation for 
College Students mini-project. 
The central architectural decision: Use a modular monolith with polyglot persistence, rather than 
implementing every component as an independent microservice. 
That means your application has clearly separated business modules, but they share one 
primary relational database. Redis and Neo4j serve specialised workloads alongside it. 
This will let you demonstrate advanced DBMS concepts without making the project 
unnecessarily difficult to build and maintain.

The architecture should retain the logical responsibilities from your original design while

2.1 Architecture style: modular monolith + multiple 
databases 
I would change one important aspect of your original architecture. 

=== PAGE 4 ===
You listed Auth, Profile, Matching, Booking, Feedback and Notification as separate services. 
Their responsibilities are good, but they do not need to be independently deployed 
microservices. 
For this project, use: 
One backend application, organised into independent business modules, connected to 
specialised database systems. 
Why? 
1.​ Booking, allocation and session management frequently need coordinated SQL

2.​ A separate database for every service would introduce distributed consistency problems. 
3.​ You are building one integrated application, not operating a large engineering 
organisation. 
4.​ You still get to demonstrate multiple databases and well-defined service boundaries. 
Your API Gateway remains the single entry point logically. It can be implemented as the API 
boundary of your backend rather than a separate deployment.

5.3 Recommendation pipeline 
 
 
The distinction between Neo4j and SQL is important: 

=== PAGE 19 ===
Neo4j identifies relevant relationships. MySQL determines whether the recommendation is 
actually eligible. 
For example, Neo4j might discover a mentor who is highly relevant but has already reached 
their mentorship capacity. MySQL should exclude that mentor from the final results.

This is a feature I strongly recommend adding.

This makes the recommendation engine understandable and gives you a good demonstration of

5.5 Keep Neo4j synchronised with MySQL 
This is another important engineering decision. 
Suppose Mentor A updates their skills. 
The flow should be: 
1.​ The profile update is committed to MySQL. 
2.​ The same SQL transaction records an event in a transactional outbox. 
3.​ A background worker reads that event. 
4.​ The worker updates the corresponding Neo4j nodes and relationships. 
5.​ Relevant Redis cache entries are invalidated. 
6.​ The recommendation engine uses the updated graph data. 
This approach avoids independently writing to MySQL and Neo4j and hoping both writes 
succeed. 

=== PAGE 20 ===
Neo4j may briefly contain an older representation, so the graph should be treated as an
