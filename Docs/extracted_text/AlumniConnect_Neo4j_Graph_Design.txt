Neo4j Graph Design
Specification
Nodes, labels, relationships, properties and traversal patterns
Project: Alumni-Student Mentorship and Mock Interview Platform
Document: Graph data model and implementation specification
Version: 1.0 | Date: 02 November 2026
Design position
Neo4j is a specialised recommendation projection. MySQL remains the authoritative store for identities, skills,
availability, requests, allocations, bookings, sessions and feedback. Neo4j discovers relevant relationship paths;
MySQL validates business eligibility.
Prepared from the supplied Alumni-Student Mentorship Platform: DBMS Project Blueprint. It expands the blueprint into an
implementable Neo4j design, with additional engineering decisions explicitly identified as recommendations.

1. Purpose, scope and design decisions
This document specifies the graph data model for AlumniConnect. The graph is designed around the platform
capability identified in the project blueprint: discovering suitable alumni through connected students, skills,
mentorship domains, companies, departments and prior mentorship relationships.
The goal is not to copy every MySQL table into Neo4j. The graph should represent the connected data needed for
relationship-driven discovery and provide explainable paths behind mentor recommendations.
1.1 Goals
• Represent students, alumni mentors and shared reference entities as nodes with stable identifiers.
• Represent skill, domain, department, company and mentorship-history connections as typed relationships.
• Support multi-dimensional mentor discovery rather than single-skill exact matching.
• Return candidate mentor IDs and the relationship evidence that explains each candidate.
• Keep graph updates reliable through a MySQL transactional outbox and idempotent projection worker.
• Keep allocation, booking, availability and other transactional decisions in MySQL.
1.2 Scope boundary
In scope for the Neo4j projection
Not authoritative in Neo4j
Student and mentor graph profiles; shared identity link
Passwords, authentication secrets, access tokens
Student and mentor skill relationships
Authoritative skill catalogue and profile editing
Student domain interests and mentor domain expertise
Mentorship requests and request approval state
Mentor company and department connections
Availability slots, booking locks and calendar conflicts
Confirmed mentorship history for career-path traversal
Booking/session state transitions and feedback records
Graph candidate retrieval and explanation evidence
Final mentor eligibility, allocation and capacity decisions
Non-negotiable rule
A recommendation is not an allocation. A mentor discovered by Neo4j can still be ineligible because of capacity,
status, availability, policy or a conflicting allocation. The API must verify those conditions against MySQL before
presenting a final actionable result.
1.3 Source-derived decisions vs implementation recommendations
Directly specified by the supplied blueprint: Neo4j represents Student, Mentor, Skill, Domain, Company and
Department; it uses the named relationships documented in Section 5 of the blueprint; recommendation
dimensions include skill similarity, domain relevance, experience, career relevance, mentor quality and capacity;
MySQL remains authoritative; graph synchronization follows a transactional outbox.
Implementation recommendation in this document: add a lightweight User node and profile-link relationships to
reflect the blueprint's common identity model; use stable MySQL IDs as graph keys; keep recommendation run
history in MySQL; use source-version fields to prevent out-of-order projection updates. These are design choices
to make the model safer to implement, not claims that the blueprint already defines these exact Neo4j
structures.

2.1 Read path: mentor discovery
The application reads the student profile and eligible criteria from MySQL, asks Neo4j for relationship-based
candidates, then validates the candidate IDs against MySQL. The API can combine graph relevance with
authoritative ratings, completion outcomes, current capacity and scheduling constraints.
2.2 Write path: profile changes
A profile update is committed in MySQL together with an outbox event in the same SQL transaction. A worker
consumes the event and updates Neo4j. Related Redis entries are invalidated. This avoids a fragile dual-write in
which an application writes MySQL and Neo4j independently.

or capacity enforcement. Those operations must revalidate and commit in MySQL.

3. Graph modelling principles
3.1 Nodes
A node represents an entity that has an identity in the graph. Examples: one student, one mentor, one skill, one
mentorship domain, one company or one department. Each projected node should have a stable ID copied from
its corresponding MySQL record.
3.2 Labels
A label classifies a node and helps queries express the type of entity being matched. Use labels such as User,
Student, Mentor, Skill, Domain, Company and Department. A node may carry more than one label: a graph
identity node may have User plus Student or Mentor labels only if the single-node profile approach is selected.
This specification instead separates User from Student and Mentor profile nodes to mirror the project blueprint's
common account and role-specific profile concepts.
3.3 Relationships
A relationship is a typed, directed connection between two nodes. Relationship direction should reflect the
business meaning, not a visual convenience. For example, the design uses (Student)-[:HAS_SKILL]->(Skill) and
(Mentor)-[:HAS_SKILL]->(Skill). A shared skill is found by traversing from the student to a skill and back to a
mentor.
3.4 Properties
Properties are key-value attributes on either nodes or relationships. Put stable entity attributes on nodes (for
example, mentor job title or skill name). Put facts that describe a particular connection on the relationship (for
example, a student's proficiency in a skill or the period of a mentor's employment at a company).
3.5 Traversal
A traversal follows one or more relationships from a starting node to discover connected nodes. Mentor
discovery is a natural traversal problem because the answer depends on paths such as Student -> Skill <-
Mentor or Student -> Department <- Mentor, not just on independent records.
3.6 Graph projection rather than table replication
• Project only attributes required for discovery, ranking evidence and safe display.
• Do not reproduce all relational columns merely because they exist in MySQL.
• Do not keep a second authoritative copy of request, booking or session state.
• Use IDs, not names, as matching keys. Names can be renamed or duplicated.
• Keep node and relationship types stable; do not create a new relationship type for every skill or domain.

5.1 Why relationship properties matter
A skill link has meaning in the context of a particular person. A student can be intermediate in Python while a
mentor is advanced in Python. The Skill node should contain the canonical identity of the skill; the HAS_SKILL
relationship records the proficiency and experience of that specific person.
Likewise, a mentor may work at the same company at different times or hold different positions. The WORKS_AT
relationship stores the employment period and title rather than forcing those facts onto the Company node.
5.2 MENTORED_BY must represent confirmed history
Create MENTORED_BY only after a mentorship allocation has been confirmed by the relational workflow. Do not
create it when a student merely views a mentor, receives a recommendation, submits a request, or has a
pending request. Keep pending/rejected request state in MySQL.

6.2 Direction conventions
• Use Student -> Skill and Mentor -> Skill for HAS_SKILL. A shared skill traversal enters Skill from one side and
leaves toward the other profile.
• Use Student -> Domain for INTERESTED_IN and Mentor -> Domain for SPECIALIZES_IN.
• Use Student -> Department for STUDIES_IN and Mentor -> Department for ALUMNI_OF.
• Use Mentor -> Company for WORKS_AT.
• Use Student -> Mentor for MENTORED_BY, because the relationship reads as “the student is mentored by this
mentor”.
6.3 Avoid unbounded traversals
For the first release, most recommendation paths are one to three relationships long. Prefer explicit patterns
such as the ones above. Avoid unrestricted patterns such as [:RELATED_TO*] without a maximum depth. If
variable-length traversals are introduced later, specify a bounded range, filter returned paths, and measure the
effect with PROFILE.

12. Recommendation API integration
Treat Neo4j as candidate generation and evidence retrieval. The backend owns orchestration and final
decision-making. A recommended request flow is:
Step 1 - Read student context. Load the student profile, active skills, target domains and policy filters from
MySQL.
Step 2 - Retrieve graph candidates. Run the multi-factor Cypher traversal and request a candidate set larger
than the final page size (for example, top 30 candidates for a final top 10).
Step 3 - Validate candidates in MySQL. Confirm that the mentor is active, eligible, not blocked, has remaining
capacity, meets role/domain rules and is not disqualified by current allocations or policy.
Step 4 - Enrich ranking. Retrieve authoritative rating aggregates, feedback quality signals, completed-session
outcomes and other non-graph scoring fields from MySQL.
Step 5 - Produce explanations. Convert graph evidence into reason strings and combine it with SQL-derived
signals.
Step 6 - Persist recommendation history. Store the recommendation run and candidate snapshot in MySQL if the
project needs to answer what was recommended at a particular point in time.
Step 7 - Cache carefully. Cache results in Redis with a short TTL and invalidate them when student skills, mentor
skills, domains or eligibility-relevant fields change.

13. Synchronisation: MySQL to Neo4j
The blueprint specifies a six-step flow: commit the profile update in MySQL, record an outbox event in the same
transaction, let a background worker read the event, update Neo4j, invalidate relevant Redis cache entries, then
allow recommendations to use the updated graph. This section turns that flow into operational rules.
13.1 Transactional outbox event
A profile update transaction should write both the business row changes and a small outbox event. If the
transaction rolls back, neither the profile update nor the event is visible. A worker polls or subscribes to
committed outbox events and applies them to Neo4j.

13.2 Worker processing rules
• Read the event and payload from the committed MySQL outbox.
• Validate the event schema and all stable IDs before issuing Cypher.
• Use a Neo4j transaction for each logical projection update or bounded batch.
• Make the update idempotent: reprocessing the same event must not duplicate nodes or relationships.
• Apply sourceVersion checks so an older event cannot overwrite newer state.
• After Neo4j commits, mark the outbox event delivered. If it fails, retry with backoff and retain an error record.
• Invalidate related Redis keys only after the MySQL change is committed; retries should be safe.

14. Lifecycle rules and graph hygiene
14.1 Create
Create the node from a source-of-truth record, then create the relevant relationships once both endpoints are
known. Use MERGE on stable identifiers, not names.
14.2 Update
Update mutable node attributes with SET. Update relationship properties when the source relationship changes.
For a full collection update (for example, all current mentor skills), remove stale edges and recreate the current
set in one idempotent projection operation.
14.3 Deactivate
A profile deactivated in MySQL should no longer be recommended. Mirror the state with `isActive = false` and
make every candidate query filter active mentors. This is a discovery filter, not a substitute for MySQL eligibility
validation.
14.4 Delete
Prefer an explicit soft-delete/deactivation projection when historical mentorship paths or auditability matter.
Physically delete a graph node only when the source deletion policy requires it and no retained history needs the
node. `DETACH DELETE` removes all incident relationships, so use it only after confirming that all downstream
graph paths can be discarded.
14.5 Rename reference data
A Skill or Domain rename should update the existing node by its stable ID. Do not create a new node because a
label spelling changed. If two reference records are merged in MySQL, update the projection so old edges point
to the canonical node, then remove the obsolete node after verifying it is unused.
14.6 Avoid duplicate relationships
For relationship types whose endpoints can have at most one logical edge, use `MERGE (a)-[r:TYPE]->(b)` and
then set properties. Where multiple real-world records may exist between the same endpoint pair (such as
repeated employment periods or multiple allocations), include a stable source record key in the relationship
pattern, for example `employmentKey` or `allocationId`.

15. Query performance and tuning
15.1 Start from a selective anchor
Anchor queries on an indexed stable ID such as `Student.studentId` or `Mentor.mentorId`. Avoid starting with
every Skill or every Mentor node and then filtering late. Unique constraints on IDs should support selective
lookups.
15.2 Keep patterns bounded
• Use explicit path patterns for the most common match dimensions.
• Filter inactive profiles and inactive reference nodes as early as practical.
• Collect distinct node IDs/names so multiple paths do not overcount the same evidence.
• Return only the fields needed by the API, not full nodes or entire paths by default.
• Set a candidate limit; then apply authoritative SQL eligibility and ranking.
15.3 Use EXPLAIN and PROFILE
Use EXPLAIN to inspect the planned operators without executing the query. Use PROFILE in a controlled test
environment to execute and inspect actual rows, database hits and operator work. Compare the query plan
before and after adding an index or changing the traversal shape. Record the test dataset size and Neo4j version
with every benchmark.

16. Security, privacy and access boundaries
The graph is a recommendation projection, not a second user-management database. Apply data minimisation:
replicate only the profile facts needed for candidate matching and safe display.
• Never project passwords, password hashes, access tokens, refresh tokens, OTP secrets or authentication
challenge values into Neo4j.
• Avoid copying private contact information unless a documented use case and access policy require it. Prefer a
public display name and profile identifier.
• Keep free-text feedback and private review comments in MySQL; recommendation queries normally need
aggregate quality signals, not the original text.
• Use a dedicated Neo4j application account with the least privileges required for read/write projection
operations.
• Use TLS for database connections where applicable, store credentials in environment secrets, and never commit
passwords to the repository.
• Parameterise Cypher values. Do not interpolate user-controlled strings into query text or dynamic
labels/relationship types.
• Log event IDs, source IDs and processing status. Avoid logging unnecessary personal data or entire profile
payloads.

20. Final design summary and glossary
20.1 Final recommended schema at a glance
Nodes: User, Student, Mentor, Skill, Domain, Company, Department.
Relationships: HAS_STUDENT_PROFILE, HAS_MENTOR_PROFILE, HAS_SKILL, INTERESTED_IN, SPECIALIZES_IN,
WORKS_AT, STUDIES_IN, ALUMNI_OF, MENTORED_BY.
Core traversals: Student -> Skill <- Mentor; Student -> Domain <- Mentor; Student -> Department <- Mentor;
Student <- Domain <- Peer -> Mentor through confirmed mentorship history; Mentor -> Company.
Operational model: MySQL source of truth; transactional outbox; idempotent worker; eventually consistent Neo4j
projection; Redis cache invalidation; MySQL final eligibility checks.
20.2 Key design decisions to defend in a project review
• Why use Neo4j? Mentor discovery depends on connected facts. Graph traversals reveal shared skills, interests,
alumni affiliation and mentoring paths directly.
• Why not copy all MySQL tables? Neo4j is a specialised projection for recommendation paths. Transactional
records remain relational and authoritative.
• Why store properties on relationships? Proficiency, employment period and mentorship status describe the
connection between two entities, not the shared entity itself.
• Why keep MySQL in the final loop? Capacity, availability, ratings and current business status can change; the
graph can be slightly stale.
• Why an outbox? It prevents a committed MySQL update from being lost just because Neo4j or the worker is
temporarily unavailable.
