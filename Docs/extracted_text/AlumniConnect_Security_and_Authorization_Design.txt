A signed-in role is not enough. Every protected operation must also verify the caller’s ownership, participation or assignment to 
the specific resource, and the resource’s current business state. FastAPI enforces this on the server for every request.

01 / Security architecture and trust boundaries
AlumniConnect is designed as a three-tier application with one logical API boundary. Student, mentor and 
administrator portals call FastAPI. The browser does not connect directly to MySQL, Redis or Neo4j. The API is the 
security enforcement point for authentication, authorization, input validation, resource scoping and response 
shaping.

1.2 Non-negotiable trust boundaries

The authenticated principal is established by the server from a validated session or token; a request body cannot 
choose its own user ID or role.

Authorization is enforced in FastAPI for every protected operation, even when a user interface hides the action.

Resource access is scoped by ownership, participation or assignment; knowing a numeric record ID is not proof 
of access.

A mentor recommendation, Redis cache hit or frontend calendar preview is not an access grant or business 
approval.

Sensitive data is returned through purpose-built projections; public mentor discovery does not return account, 
contact or administrative fields.

2.1 Common account identity
The conceptual model uses one User Account as the authentication identity. Student Profile and Mentor Profile are 
separate role-specific extensions linked to that account. This avoids duplicating credentials while retaining distinct 
academic and professional attributes.

2.3 Authentication flow
1.
User submits login credentials to the FastAPI authentication endpoint over HTTPS.
2.
Backend normalizes the identifier, retrieves the account and verifies the submitted password against the stored 
one-way hash.
3.
Backend verifies account status and creates the configured session/token context.
4.
Every subsequent request validates the session/token and resolves a Principal containing immutable user_id, 
role/permissions and relevant account status.
5.
Protected endpoint applies role permission plus resource ownership/participation and current state checks 
before accessing or returning data.
6.
Logout, password reset, role change or account suspension must revoke or invalidate applicable 
sessions/tokens according to the approved session design.

2.4.1 Suspension and reactivation procedure
A status change is a privileged identity operation. It must not be implemented as a generic editable field on a profile 
endpoint.
7.
An administrator invokes the explicit account-status permission and supplies the target account, requested 
status and a reason.
8.
FastAPI verifies the administrator principal, permission and target account; the operation is written to MySQL 
with an audit record in the same transaction.
9.
After commit, applicable sessions/tokens are revoked or invalidated according to the selected authentication 
design. If the system uses stateless tokens, the team must define how current account status or a token/session 
version is rechecked.
10. New write operations are denied for a suspended/disabled account. Existing requests, allocations, bookings, 
sessions, feedback and reviews remain stored; historical reads are governed by the relevant resource policy.
11. Reactivation is a separate audited administrator action. It restores only the account’s assigned permissions; it 
does not reopen terminal requests, cancelled bookings or completed sessions.
STATUS-CHECK PLACEMENT
Check ACTIVE status during authentication and again in sensitive write services. A long-lived token or cached account card must 
not preserve access after suspension.
Source alignment: Business Rules Catalogue ACC-001 through ACC-007 (pp. 5-6); PRD NFR-01 (p. 9); Application Architecture section 13.1 (p. 
17).

03 / Authorization model: RBAC plus resource context
Use role-based access control (RBAC) to determine which capabilities a role may invoke. Add resource-level checks 
to decide which specific record the caller may act on. Add state checks to decide whether that action is currently 
valid. This combined approach reflects the project documents’ requirement that a protected action be authorized for 
both the signed-in role and the relevant record.
Figure 2. Every protected operation follows the same authorization decision sequence.
3.1 Three authorization dimensions
Dimension
Question
AlumniConnect example
Role permission (RBAC)
May this role perform this type of action?
Only Mentor may accept or reject a mentorship request.
Resource relationship 
(ownership / participant / 
assignment)
May this principal act on this particular record?
The mentor may decide only a request addressed to their 
mentor profile; student may cancel only their own pending 
request.
Business state / context
Is the action permitted in the current lifecycle 
state?
A request must still be PENDING; feedback requires a 
completed session and a real participant.
3.2 Default-deny decision policy

No route or operation is public unless explicitly listed as public/unauthenticated.

No role has implicit permission because it can see a page or because a record ID is known.

An unrecognized role, missing profile, inactive account, failed ownership check or invalid state results in denial.

Administrator powers are explicit. Administrator is not a universal impersonation role and does not become a 
student or mentor automatically.

Permission checks are repeated at the API/service boundary even when database constraints, route guards or 
frontend visibility exist.
3.3 Recommended authorization decision contract
authorize(request):
    principal = authenticate_and_resolve_server_side_identity(request)
    require(principal.account_status == ACTIVE)
    permission = permission_for(request.route, request.method)
    require(permission in principal.permissions)
    resource = load_resource_with_scoped_lookup(request.path_parameters)
    require(resource_exists_and_is_visible_to(principal, resource))
    require(resource_state_allows(permission, resource))
    return execute_with_scoped_repository(principal, resource)
The exact response code for a failed check depends on whether the caller is unauthenticated, lacks a role permission, does not own the 
resource, or requests an invalid state transition. Avoid returning private existence/ownership details to unauthorized callers.

3.4 Role assignment versus profile existence
A User may have a Student Profile, a Mentor Profile, or both if the final account policy permits it. The conceptual ER 
model allows each profile extension to be optional (0..1). The source documents do not completely settle whether a 
person may hold both operational roles simultaneously. Keep role assignment and profile existence explicit; do not 
infer a role merely because a profile row exists.
DECISION REQUIRED
Confirm whether a single account may simultaneously be Student and Mentor, whether Administrator can be combined with 
either role, and how the UI selects an active role context. The authorization service should support explicit role/permission 
assignments rather than hard-coded assumptions.

Source-aligned
Mentor role + Mentor Profile

participant sessions.
Source-aligned

[D] Decide

[R] Recommended

assignment rather than accepted as an arbitrary client-supplied role string.

5.1 Action boundaries that must not be conflated

Recommendation is not an allocation. Neo4j returns candidates; MySQL revalidates account status, visibility, 
capacity and current eligibility.

Request is not allocation. A student creates a request; only an addressed mentor accepts it, and allocation is 
created by the controlled transaction.

Booking is not a completed session. A booking is a planned appointment; the mentor records the actual outcome 
later.

Session feedback is not a mentor review. Either real participant may provide session feedback; the student 
alone authors the mentor review after a completed session.
5.2 Cancellation and rescheduling policies
The source documents specify that cancellation initiator, cutoff, slot reopening and rescheduling policy require a 
project decision. Until the team confirms those policies, expose only the minimum supported transitions and reject 
ambiguous actions. Preserve the original booking as historical data; do not overwrite it with a replacement booking.
Source alignment: Business Rules Catalogue request, booking, session and feedback rules; Use Case Model sections 10-11; Workflow and State 
Diagrams lifecycle/transaction specifications.

Feedback authorship and access must remain separate. Either actual participant may submit session feedback 
under the feedback rules. A mentor review is the student’s rating of the mentor after a completed session. The 
source documents do not fully specify whether free-text feedback is visible to both participants, only to the mentor, or 
only to administrators; define this as a product privacy decision before building the read endpoints.
FIELD-LEVEL SECURITY IS NOT A FRONTEND CONCERN
A user interface may choose not to render a field, but the API response should not contain it in the first place. Use role-aware 
response schemas and SQL projections.

08 / FastAPI enforcement architecture
FastAPI is the single logical API boundary in the modular-monolith design. The frontend may use role-aware routes 
for usability, but every protected endpoint repeats authentication, role, resource and state checks on the server.
8.1 Recommended request pipeline
12. Validate transport and request shape; reject malformed identifiers and unsupported fields.
13. Authenticate the session/token and create a trusted Principal object from server-side claims and current account 
state.
14. Apply route-level permission (for example, mentor.requests.decide). Default-deny any route without an explicit 
policy.
15. Load the target record using a scoped repository method that includes the expected owner, participant or 
assignment relationship.
16. Validate lifecycle state, account status, visibility, capacity or other policy guards at the point of action.
17. Execute the business operation through the module/service and MySQL transaction boundary.
18. Return only the response fields authorized for this principal and action; record audit/telemetry where required.
8.2 Illustrative FastAPI policy pattern
from dataclasses import dataclass
from enum import Enum
from fastapi import Depends, HTTPException, status
class Role(str, Enum):
    STUDENT = "STUDENT"
    MENTOR = "MENTOR"
    ADMIN = "ADMIN"
@dataclass(frozen=True)
class Principal:
    user_id: int
    role: Role
    account_status: str
def require_roles(*allowed_roles):
    async def dependency(principal=Depends(get_current_principal)):
        if principal.account_status != "ACTIVE":
            raise HTTPException(status_code=403, detail="Account is not active")
        if principal.role not in allowed_roles:
            raise HTTPException(status_code=403, detail="Forbidden")
        return principal
    return dependency

8.4 Avoid common API authorization defects

Never trust user_id, student_id, mentor_id, role, owner_id, status or is_admin supplied by a client body as proof 
of authority.

Prevent mass assignment: accept only fields that the endpoint is designed to change; never bind arbitrary input 
to ORM models.

Use scoped repository methods rather than loading by ID and relying on the caller to remember a later owner 
check.

For unauthorized record IDs, return a consistent not-found/forbidden policy that does not reveal private data or 
ownership information.

Re-check sensitive state immediately before writes; cached or previously loaded state may have changed.

09 / MySQL, Redis and Neo4j access boundaries
9.1 MySQL / InnoDB
MySQL is the authoritative store for users, roles, profiles, skills, requests, allocations, availability, bookings, sessions, 
feedback, reviews, notifications and audit history. The API must enforce row/record ownership in its queries and 
procedures; database constraints reinforce integrity but do not replace authorization.
Control
Recommended implementation
Runtime credentials
Use a private runtime account with only the privileges needed by the API. Do not use the schema owner/root account from 
the web process.
Migration credentials
Keep schema migration/DDL privileges separate from routine request handling.
Worker credentials
Give the background worker only the tables/procedures required to claim outbox events, update delivery/projection status 
and write required records.
Public directory
Use a dedicated view or repository projection containing approved public columns; restrict direct base-table exposure where 
practical.
Privileged procedures
Expose narrow stored procedures for sensitive lifecycle operations; validate actor/resource context and current state inside 
the operation where appropriate.
Integrity constraints
Use foreign keys, unique constraints, CHECK constraints and restrictive deletes to prevent invalid relationships and preserve 
history.
Audit
Record actor, target, action, timestamp, outcome and reason for privileged account/role changes and significant admin 
actions.
9.2 Redis

Authenticate and authorize every API request before serving a cached value. Cache keys are not access-control 
tokens.

Cache only public mentor display fields in public profile keys; do not cache private contact fields, admin notes, 
credentials, tokens or confidential session notes in public payloads.

Use environment/version key prefixes and restricted Redis credentials/ACLs where supported.

Treat challenge, rate-limit and idempotency keys as operational helpers, not sole durable protection. MySQL 
constraints and application validation remain necessary.

On account suspension, visibility change or relevant profile update, invalidate affected profile/recommendation 
caches after the authoritative MySQL commit.
9.3 Neo4j

The browser and ordinary user principals do not receive direct Neo4j credentials or unrestricted Cypher access.

The discovery module may query graph relationships to return mentor candidates and explanations; it must 
validate each candidate against current MySQL status, privacy, visibility, capacity and other current rules.

Graph projection updates are driven by committed outbox events and may be eventually consistent. A stale 
graph result cannot authorize a request, allocation or booking.

Use a restricted application graph identity. Separate projection-write access from discovery-read access if the 
deployment supports it.
9.4 Background worker / service identity
The outbox worker is an internal service principal, not a fourth human role. It should process only committed events, 
use stable event IDs, be idempotent on retries and have narrowly scoped access to the operations it performs. Do 
not let a user choose the worker’s target recipient, event type or internal action without server-side validation.
CROSS-STORE RULE
If Redis or Neo4j disagrees with MySQL, MySQL wins. Neither supporting store is an authorization authority. The browser never 
talks directly to the data stores.

11 / Privacy, data lifecycle and secure operations
11.1 Least-privilege data exposure

Students see approved public mentor profile attributes and their own private records; mentors see relevant 
student information for accepted allocations and sessions.

Do not expose private email, phone, internal notes or admin-only audit fields in the public mentor directory.

Review text and session notes are access-controlled and should not contain passwords, tokens, financial 
account information or unrelated sensitive information.

Do not treat a Redis cache key, Neo4j path or guessed resource ID as a permission check.
11.2 Retention and deactivation
Use soft deactivation and restrictive deletes. Deactivating an account must not cascade-delete requests, allocations, 
bookings, sessions, feedback or reviews. Preserve business history and define a separate retention/anonymization 
policy for personal data. If deletion is legally or operationally required, the project needs a controlled anonymization 
procedure that preserves referential integrity and legitimate aggregate reporting while minimizing personal identifiers.
11.3 Secrets and deployment
Area
Baseline safeguard
Network boundary
Keep MySQL, Redis and Neo4j on private networks; only the backend/worker should connect.
Configuration
Use environment-specific secret configuration; do not commit DB passwords, signing secrets or API keys.
Transport
Use HTTPS between browser and API; protect service-to-database connections according to the deployment environment.
Credential storage
Store salted one-way password hashes only; never log passwords or session/token secrets.
CORS / origins
Allow only the expected frontend origins; avoid broad wildcard origins when credentials are used.
Cookie/session policy
Choose secure cookie or token handling deliberately; define expiry, revocation and CSRF protection consistent with the 
selected mechanism.
Logging
Log request correlation ID, actor ID, module, operation outcome and duration; redact secrets and sensitive payloads.
Administrative export
Restrict exports, return only needed columns and record access to sensitive exports where practical.
11.4 Operational monitoring

Track authentication failures, authorization denials, role changes, account suspensions and unusual access 
patterns.

Track access to admin views and sensitive exports where practical.

Monitor outbox backlog and worker failures without logging complete private payloads.

Monitor Redis/Neo4j service credentials and connectivity; outage must not cause the API to bypass 
authorization.

Use correlation IDs to connect API requests, MySQL audit records and outbox events.
POLICY GAP
The documents require privacy-aware access and history preservation, but do not define exact retention periods, password-reset 
rules, token lifetime, MFA requirements, data residency or a formal incident-response process. Treat these as open decisions, 
not established project requirements.
