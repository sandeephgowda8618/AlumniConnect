that exercise the outbox and secondary-store projections. Run performance tests only after correctness and data 
fixtures are stable.

1. Purpose, scope and test principles
This document defines how AlumniConnect will be verified before the DBMS project is accepted. It combines 
functional, database, concurrency, security, cross-store, performance and recovery tests into one plan. The 
objective is not merely to prove that the interface renders or that individual API endpoints return 200; it is to 
prove that the platform preserves the business rules and database consistency established in the supplied design 
documents.
1.1 Test objectives

Verify referential integrity, uniqueness, domain constraints, lifecycle states and historical-record retention in 
MySQL.

Prove ACID transaction boundaries for request acceptance, booking, cancellation, session outcome, 
feedback/review and outbox event creation.

Prove that simultaneous operations cannot exceed mentor capacity, allocate one request twice, double-book a 
slot or create overlapping participant bookings.

Verify that role-based permissions are combined with record ownership, assignment and participant checks at 
the FastAPI boundary.

Verify cache-aside behaviour, TTL expiry and outbox-driven Redis invalidation without allowing Redis to 
become business authority.

Verify Neo4j node/relationship identity, traversal output, projection idempotency, source-version ordering, 
rebuild and MySQL eligibility filtering.

Measure response latency, throughput, errors, database/graph/cache behaviour and background-worker lag 
using repeatable workload and dataset conditions.

Prove graceful recovery when Redis, Neo4j, the notification provider or the outbox worker is unavailable.
1.2 Scope included in the core release
AREA
IN-SCOPE VERIFICATION
Identity and access
Registration/sign-in, role assignment, account status, role/profile 
linking, password handling and access denial.
Profiles and catalogues
Student/mentor profiles, department, company, skills, domains, 
many-to-many links and public/private projections.
Mentor discovery
SQL filters, Neo4j traversal, candidate explanation, MySQL 
eligibility/capacity filtering and optional Redis result cache.
Requests and allocation
Submit, accept, reject, pending cancellation, capacity checks, 
unique allocation and history.
Availability and booking
Slot publication, overlap validation, duplicate retry, booking 
confirmation/cancellation and slot state.
Sessions and feedback
Scheduled/completed/cancelled/no-show outcome; participant 
feedback; completed-session mentor review.
Notifications and operations
Transactional outbox, notification recipients, worker retries, audit 
records and admin reports.
Supporting stores
Redis cache/temporary state and Neo4j relationship projection.
1.3 Explicitly out of scope for core acceptance
Video-conferencing infrastructure, real-money payments, independent microservice deployment and Redis Stack 
vector/semantic discovery are outside the core release described by the PRD. Vector search may be tested as a 
Phase 2 extension only after the SQL and graph recommendation path passes.
System boundary: the project uses a modular monolith. The browser calls FastAPI; FastAPI coordinates MySQL, Redis and Neo4j. 
MySQL is authoritative for identities, requests, allocations, availability, bookings, sessions, feedback, reviews, notifications and 
audit records.

4.3 Data management rules

Use synthetic accounts and profile text; do not seed production email addresses, phone numbers, tokens, 
password hashes or private notes.

Every test should declare preconditions and either create an isolated fixture or reset the required records 
before execution.

Use stable numeric IDs or deterministic UUIDs in tests so SQL, Redis keys, Neo4j nodes and logs can be 
correlated.

Keep separate Redis key namespaces and Neo4j databases for dev, CI and staging; tests must not flush a shared 
environment.

Freeze or record the timezone, server clock assumption, database isolation level, schema version, Redis 
configuration and graph index state for reproducibility.

Preserve failure evidence before cleanup: transaction logs, SQL row snapshots, outbox rows, Redis TTL/key 
state, Neo4j results and worker logs.

6.1 Domain invariants to assert after test runs

Each User has no more than one Student Profile and no more than one Mentor Profile, subject to the approved 
role policy.

Every request identifies one student, one mentor and a valid mentorship domain/objective; request status is 
one of PENDING, ACCEPTED, REJECTED or CANCELLED.

At most one Mentor Allocation is created from a request; active mentor capacity is not exceeded.

Every confirmed Booking references the correct student, mentor, availability slot and valid active allocation 
where that booking type requires it.

No active booking duplicates one slot; no confirmed appointments overlap for the same student or mentor 
under the half-open interval rule.

Every Mentorship Session references a valid Booking; feedback is by actual participants after the session has 
taken place; mentor review requires a completed session.

Notification/outbox/audit records are tied to a committed business action and preserve required history.

8.2 Concurrency test execution method
1. Use at least two independent MySQL connections; do not simulate a race with sequential calls in one session.
2. Prepare one immutable test fixture per race (request, slot, allocation, student and mentor) and verify its 
preconditions before the race.
3. Use a synchronization barrier so both transactions reach the contested operation at nearly the same time.
4. Capture transaction start/end times, connection IDs, lock wait, SQL error, API response and relevant rows after 
both operations finish.
5. Repeat each scenario multiple times under the configured InnoDB isolation level and final indexes; record test 
count and observed distribution.
6. Assert the final invariant, not only the HTTP result: exact counts/statuses, no duplicate outbox, and no orphan 
session.

11.3 Recommended workload mix
For a repeatable initial benchmark, the team may begin with a balanced workload such as: 20% profile/catalogue 
reads; 20% mentor discovery/recommendations; 15% request lifecycle; 20% availability/booking; 10% 
session/feedback/history; 10% admin reports; 5% authentication/account operations. This mix is a suggested test 
profile, not a supplied requirement. Record the actual mix in every run.
11.4 Performance experiment procedure
1. Freeze the build SHA, schema migration version, MySQL isolation setting, Redis TTL/configuration, Neo4j 
version/index state and dataset size.
2. Run a warm-up phase; separate cold-cache and warm-cache measurements.
3. Ramp users gradually to the 50-user PRD baseline; record p50/p95/p99, throughput and error rate at steady 
state.
4. Capture application, MySQL, Redis, Neo4j and worker metrics over the same time window.
5. Repeat at least three benchmark runs if practical; report median and spread rather than one best result.
6. For any optimization, compare before/after against the same dataset and workload; retain EXPLAIN/PROFILE 
evidence.

Neo4j may be unavailable, stale or rebuilt without corrupting committed business state.

The 50-concurrent-user profile and p95 response thresholds are proposed initial PRD baselines, not 
contractual guarantees or measured results.

The exact TTLs, retry counts, lockout thresholds, cancellation windows, mentor capacity and review-edit policy 
remain configurable team decisions unless separately approved.

Code snippets/table/column examples in prior specifications are templates; final tests must target the project’s 
migrated schema and implemented endpoint contract.

Optional Redis Stack vector search is Phase 2 and is not a blocker for core acceptance.
